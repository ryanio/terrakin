# packages/server/

The front door. Parses, authenticates, rate limits, runs the sim, persists, and broadcasts. It holds no game rules. How the pieces fit: [docs/architecture.md](../../docs/architecture.md).

## Rules

### The world

- Every world change goes through `WorldService.run()`: `prepare` (check), `store.appendInput` (persist), `commit` (mutate), broadcast. A failed write never leaves memory ahead of the log. Never mutate `service.state` directly. A dry run (`dry: true`) goes through `act()` and `run(input, true)` like a real one and stops after `prepare`; an offline resident is checked against the sim's `asJoined` view, and nothing brings them back online. `hash()` is cached per `seq`, which is only safe because nothing else changes the world.
- Purses, inventories, points, and jobs are private. The events in `PRIVATE_EVENTS` (`world-wire.ts`) go only to the resident they name (a lesson's `recipe_learned` to its teacher too), never in a broadcast or anyone else's answer. Use `eventsFor` and let `run()` route them. A profile shows levels and a title, never points, today's counts, or firsts; those are `GET /v1/progress`'s, which answers only its own caller. The treasury view is public but shows gifts without amounts.
- `toWire` keeps `job_total`, `job_edition_set`, and `event_ticked` off the wire.
- Each system a world opens with a logged switch is absent from the wire of a world that never logged it, so such a world reads as it always did. Keep a new field behind its state (`state.progress`, `state.jobs`, `state.circles`, `clayOpen`, `lands`). `levels.test.ts`, `jobs.test.ts`, `circles.test.ts`, and `pottery.test.ts` pin the reads of a world without the switch key by key.
- `tick()` logs each one-time switch from one table: `PRESENCE_SWITCH`, then `DAY_SWITCHES` in order, run by `switchOn`. A new switch goes in the table where it has to come.
- Both adapters spread `WORLD_SWITCHES` (`world-switches.ts`); the Worker adds its own after the spread, each with why. `world-switches.test.ts` pins what each adapter runs. Jobs wait for levels; circles for coins. Pottery (`clay`) and new lands (`lands`) are the Worker's only, so self-hosting, `pnpm dev`, and the e2e servers have neither. Plots for sale (`plotMarket`) are on in neither until Ryan says go ([decision 0365](../../docs/knowledge/decisions/0365-plots-past-the-first-are-only-bought-the-market-opens-with-i.md)). A test world opens them with `pnpm persona --open-clay`, `--open-land`, or `--open-plot-market`.
- The jobs board moves forward only, one `set_job_edition` right after a `new_day`, never mid-day. Once clay is out, `moveJobEdition` steps it one edition a `new_day` to the sim's `POTTERY_JOB_EDITION`, never skipping one.
- The lands switch logs `open_land` only when the claimable plots left fall to the sim's `LANDS.openAt` (a count, never a date), until `LANDS_TO_OPEN` runs out. `planLand` puts every number in the input, so replay never plans. A land's name comes from that list, never a resident. `planProblem` refuses a plan with no streets, a slot no walk from the Commons reaches, or, fully claimed, a plot with no way out ([decision 0357](../../docs/knowledge/decisions/0357-a-land-plan-is-refused-when-fully-claimed-a-plot-has-no-way-.md)).
- The town centre reads `downtown(state)`, never `config.width`/`config.height`, which `open_land` grows. Passing the grown config is a type error.
- Offered plots prefer ones that close nobody in, logged as a `settle` with its own `px` and `py`, so replay never moves one.
- `planWays` is pure and walks plots with the sim's `placeOf` and `placeWalk`, never a copy. `POST /v1/admin/ways` stops on `dry` or any conflict (`wayConflicts`), tells each owner whose plot changed, and logs it. Nothing applies a plan on its own.
- The board is data: no `todo` line asks for a job, and the board never goes in the check-in's digest.
- A forming circle is hidden from outsiders. Invites go only to the invitee and stewards, a forming circle's events only to its members, invitees, and the resident named (`circleAudience`, with `circleRoster` for a circle the commit disbanded), and an outsider naming one hears what a missing id gets (`hiddenCircle`). A report takes only a formed circle. A circle night's credited guests leave out the event's `kin`.
- Rolls the server adds to an input (a cast's and a kiln's `roll`, from `fairRoll` in `world-actions.ts`) use Web Crypto, rejection sampled. A dry kiln rolls nothing.
- What a resident hears about a pot comes from their own events: `fired` is read from the actor's own `inventory` event, so a co-owner opening someone else's kiln hears no pot, and `pot_sold` carries codes and numbers, never the buyer or the label.
- A `move` with `steps` is walked a tile at a time by `actWalk`, a rate-limit token per tile after the first.
- REST and link callers `arrive()`, which only notes them unless the action is `chat`. The `putter` and `build` limits (`BUILD_LIMITS`) are in memory, answer `rate_limited` with `retryAfter`, and don't count dry runs. A dry `build` or `add_floor` spends nothing (`build.test.ts`). `facing` and `routine` are in memory only.
- `set_shop_share` is logged when the share changes, so earlier purchases replay at theirs. Owner links reach the sim one pair at a time.
- A snapshot's body is `JSON.stringify`, never `canonicalJson`. The boot uses one only once verified (`format`, `REPLAY_VERSION`, SHA-256, `seq`, hash, coin supply), else falls back. Its reports carry codes and `seq`s only (`reportable`). A snapshot by hand is refused while another waits to be verified.
- Lengths of time (`MINUTE_MS`, `HOUR_MS`, `DAY_MS`) and `utcDay` come from the sim's `clock.ts`. No file here defines its own.

### Routes, errors, and storage

- Routes come from the table. Add the route to its area's file in the protocol's `src/route-table/` and its handler to that area's file in `src/handlers/` (a link route's in its feature's file in `src/links/`, id in `LinkRouteId`), then run `pnpm gen`. Handlers are typed by `AreaRouteIds`, so a missing or extra one is a compile error. `routeHandlers()` spreads `linkHandlers` last, so a route handled twice quietly uses the `links/` one. No path matching anywhere else. The dispatcher parses every input with the protocol schemas.
- Link actions go through the same `WorldService.act` and social calls as the API, so every check and filter applies, and each action after the first pays its own rate-limit token. A craft label goes through a dry run first.
- Errors are `{ error: { code, message } }` with a code from `ERROR_CODES` and a message a player could read. A typo in an action type or field gets `did_you_mean` (`suggestFor`); actions refuse a near-miss field even when the rest parses, and every other body refuses a renamed field (`renamedField`). Every other parse failure, in a body, query, path, or socket action, is answered by `plainProblem`, never zod's message. A family recipe's thing for a kind outside its family gets the world's `unknown_item` answer (`familyMiss`), on REST and the socket.
- Ids from requests are own keys. Look world records up with the sim's `own`, `residentById`, `listingById`, `goodById`, or `findBounty`, never `state.x[id]`. `SocialService` refuses inherited ids before its lookup. `ids.test.ts` sends them to every route that takes one.
- `CREATE TABLE IF NOT EXISTS` is a first boot, never a migration. A column added to an existing table needs an `ALTER TABLE ... ADD COLUMN` beside it, run every boot in a `try`/`catch`; a table whose columns come from a constant needs that pass over the same constant ([learning](../../docs/knowledge/learnings/2026-10-20-a-column-added-to-a-create-table-if-not-exists-never-reaches.md)). `schema-upgrade.test.ts` boots storage on every table as it first shipped (`first-tables.ts`). A new table adds its `CREATE TABLE` there as it ships, and an entry there is never edited to match the code. Anything else read back from before a deploy gets a test that starts from the old shape.
- SQL fits a Durable Object's limits: at most 5 terms in a compound SELECT, 100 bound values, and 100,000 bytes a statement (`SQL_LIMITS` in `sql-store.ts`). `nodeSql` refuses them too, so tests catch it. Read ids from many tables with `idsFrom`, never one long `UNION`, and cap or split any `IN (...)` list built from input ([learning](../../docs/knowledge/learnings/2026-10-08-a-durable-object-s-sqlite-refuses-a-union-of-more-than-5-ter.md)). Transactions go through `ctx.storage.transactionSync`, since a Durable Object refuses `BEGIN`.
- Sessions are append-only. The social tables never feed the sim. The collection book is written once per kind, from committed input only.
- Every notification from a resident goes through `notify()`; one from Terrakin through `systemNotice` or `takedownNotice()`.
- Never throw out of a socket callback. The `message` handler catches and replies `internal`. A failed away-log write is reported and never turns the call away.
- Every ask of the World object from the Worker goes through `askWorld` (`pages.ts`). A GET or HEAD that isn't a socket upgrade goes again once after a broken connection, a write never does, and one still unreachable is `unavailable` (503) reported as `world.fetch`. The body is read before it returns (`inHand`), since a stub's `fetch` settles on its headers. An error the object threw itself goes on through.
- A new client route needs a case in `matchPage` (`page-meta.ts`), or its HTML goes out as a 404 with `noindex`.
- Share links are built on the request's `origin`, never a hard-coded host, from ids and coordinates only (`share-links.test.ts`).
- Inject time and the network. Anything time-based takes a `now()`, and the X reader, agent link network, and card readers are injected, so tests never sleep or touch the network.
- Client IPs come from `clientIp()` on Node and `CF-Connecting-IP` on Cloudflare. Never read `X-Forwarded-For` anywhere else.
- The Node server keeps idle connections open `KEEP_ALIVE_MS`, longer than the proxies in front.
- Both runtimes. Code the Worker imports (the API, handlers, links, the world and social services, the SQL store, media, and what they import) uses no `node:fs` and no `Buffer`; `pnpm typecheck` checks it against the Workers types. It never stores a runtime global as a field: workerd refuses its own `fetch` called as a method of anything else. Default an injected fetch to `options.fetch ?? ((input, init) => fetch(input, init))` and cover the default with a test ([learning](../../docs/knowledge/learnings/2026-10-20-workerd-refuses-a-stored-global-fetch-so-musegod-heard-nothi.md)).
- `lesson-plan.ts` and `tip-plan.ts` import nothing, since `scripts/townsfolk/` loads them as they are.

### Credentials and staff

- Tokens, link keys, codes, and staff keys are stored as SHA-256 only, never logged, and shown once. Hash through `bytes.ts` (`sha256Hex`, `sha256HexSync`) and nowhere else, since stored credentials are found by that hex (`bytes.test.ts`). Link keys travel in the URL path, so mask `/v1/act/<key>` before a path reaches a log line or an error.
- A link route must not reach uploads, deletes, or key minting. A link key becomes a token only through `POST /v1/link-key/upgrade/token`, with its owner's approval ([decision 0241](../../docs/knowledge/decisions/0241-a-link-only-agent-trades-its-link-key-for-a-token-once-its-o.md)).
- Passkeys and sign-in ([RFC 0037](../../docs/rfcs/0037-account-bound-identity.md)), pinned by `signin.test.ts`:
  - The relying party is read off the request's origin, never configured.
  - A ceremony must be verified, not merely present (`not_verified`), and the counter is a high-water mark. Challenges are spent on use. The byte walks in `passkeys.ts` read lengths first and refuse rather than throw.
  - A sign-in mints a fresh token and leaves every other one working. Unbinding ends that passkey's sessions only.
  - `POST /v1/signin/others-out` is the only route that reads the caller's `tokenHash`.
  - The `passkey_bound` and `passkey_signin` notices carry only the fact and the time, and are the mitigation RFC 0037 chose over a waiting period, so don't drop them ([decision 0320](../../docs/knowledge/decisions/0320-a-passkey-notice-carries-only-the-fact-and-the-time-and-the-.md)).
  - A staff sign-in link is refused for an AI and logged without the link. Starting a sign-in has its own looser limit (`signinBegin`); finishing stays on `signin`.
- An owner's re-key is cancelled by any call the agent makes; `openRekeys` stays in memory, since it runs on every call.
- Retiring repeat joins runs on the Worker only and touches unused records only: any call ever made, and a bound passkey, count as use. Retired and merged records keep their credentials as retired, so a failed call says why; their moderation rows stay.
- `TERRAKIN_TEST_CLOCK`, `TERRAKIN_TEST_X_OEMBED`, and `TERRAKIN_TEST_CHAIN` refuse to run with `NODE_ENV=production`, and the test routes that write (`maintainer`, `grant`, `open-land`, `open-plot-market`, `open-clay`) answer loopback callers only.
- Staff identity comes only from the Worker. Staff routes are `auth: "staff"`. With Access configured, the only staff email is the one the Worker verified from the Access JWT and passed in `STAFF_EMAIL_HEADER`, which `toWorld()` drops from every incoming request first. Never read the header anywhere else, and never let a resident token count when Access is on. `staffFor` refuses `cross-site` requests, any `Origin` but the admin host's, and writes that aren't JSON. Without Access, admin.terrakin.org answers 503, and `ADMIN_ASSET_PREFIX` is a 404 on the main site.
- A staff key (`tks_`, [RFC 0026](../../docs/rfcs/0026-staff-keys.md)) acts as its maker (`staffOwner`), never beyond their role now or the key's scope (`keyAllows`), and never reaches the key routes, the world-log export, or anything in `KEY_NEVER`. Every role check, `staffResident`, and `worldStaffId` reads the maker through `staffOwner`; a new one must too.
- The deploy's Access service token ([decision 0257](../../docs/knowledge/decisions/0257-ci-s-deploy-signs-in-for-the-replay-check-with-an-access-ser.md)) is honored only for `TERRAKIN_ACCESS_DEPLOY_CLIENT`, only on an admin host, only for a GET of the world log (`adminGate`, `DEPLOY_ACTOR`). It passes in `STAFF_SERVICE_HEADER`, which `toWorld()` drops like the email header. It has no role: never give it one or name it in another route. `staff.test.ts` pins every way `cloudflare/worker.ts` hands a request to the World object.
- The world-log export (`logPage`) holds residents' words: maintainers and the deploy token only, an Access sign-in on terrakin.org, capped pages, never cached, and a bad row reported by its kind alone.
- Staff bounty inputs carry `resident` (`staffResident`, `TERRAKIN_STAFF_RESIDENTS`), so the sim can refuse a maintainer whose household is in on it.
- A recognition award (`awardGrant`, [RFC 0036](../../docs/rfcs/0036-recognition-grants.md)) needs a maintainer, a sign-in rather than a key (`KEY_NEVER`), and a resident `staffResident` names. It refuses an unknown or suspended recipient before paying. The reason goes in the moderation log, never the world log.
- Moderation actions are logged. Staff or triage acting on someone else's content goes through `SafetyService`, which writes the append-only `moderation_log` with a reason and the actor; SQLite triggers refuse its updates and deletes. Its console line names an Access sign-in only as `staff`. In the world log, `worldStaffId` turns a sign-in into an opaque `staff_` id, so no email is ever logged there.
- The dispatcher refuses writes and socket actions from suspended residents and those in a cool-down, except `safety` routes. Maintainers' and townsfolk's posts are never auto-hidden.
- `purgeMedia` and `purgeUpload` take a file down from storage first and never report success while it is still stored.
- Every takedown tells its owner once. The notice never carries staff's reason, identity, or a reporter. `ruleFor` never logs `self_harm`.
- Auth, sessions, rate limits, and the store are security-sensitive: run the `reviewer` subagent.

### Resident text and outside data

- Resident text goes through `cleanText()` and `Moderation.review()` (`moderation.ts`, [decision 0032](../../docs/knowledge/decisions/0032-lite-text-filters-at-the-edge.md)) before it's stored, logged in the world, or sent: pick its `Surface`, pass the resident (and `ipKey()` for posts), and call `commit()` once stored. A new door for text needs a line in `trust-safety.test.ts`. Pet and plot names and circle notices are filtered (`pet_name`, `plot_name`, `circle_notice`) before they're logged, and circle notices are capped by `CIRCLE_NOTICE.perDay`. Report notes run only the check for orders aimed at AI readers, since a fair note may quote what was said. Never log the text a filter saw, only its category, surface, and resident id.
- Tune the filters in `moderation-lists.ts`, with tests of sentences that must still pass. Both adapters share one `Moderation`.
- `injection.ts` turns away text written as orders to AI readers, owner codes, sign-in links, write requests to the API, and link keys. Page meta writes resident text only through escaping APIs.
- Words we write about the world (plot news, photo stories, away lines, check-in `todo` lines, link page gift lines, notices from Terrakin) are built from counts, codes, and ids, never from anyone's text.
- Held words stay held: `shownPlotName` holds a plot's name back while its writer's words are held, and a held writer's circle name shows by its id. Item labels and gift notes go out marked untrusted.
- Blocks and suspensions apply everywhere a resident reaches another: a gift, give, sale, claim, sit, teach, invite, visit, knock, cast, praise, pat, or event join across a block is refused, and lists leave out suspended residents and anyone blocked either way. The one exception is the public plot list, which leaves out only those the caller blocked (`blockedBy`), since leaving out those who blocked the caller would tell them who did. Counts never say who. A recognition award skips the block check on purpose: it is a payment, not contact.
- The live socket's `announce` sends new post ids to everyone but those blocked either way with the author. Watch sockets are capped in all and per IPv6 /48 (`PostListeners`), closed after `WATCH_MAX_MS` or `WATCH_SILENT_MS` silent, and end on revocation.
- Anything a network or an agent card sends is untrusted ([decision 0050](../../docs/knowledge/decisions/0050-agents-prove-themselves-from-their-registry-and-card-and-par.md)). Decode strictly, keep only the card's `name` (cleaned and filtered) and its `terrakin` endpoints, and never store, log, or show the rest. Matching reads who holds the agent, never the card's text. No holder address is stored: the agent's holder is compared and dropped, a character's kept only as a hash. Every read goes through `AgentLinkService`, which reserves from that day's pool before reading (`agent-links.test.ts`). On Node, card fetches go through `node-net.ts`, which refuses private addresses on the connection. A partner character's picture comes only from partner config, is fetched by the same rules (`fetchOutside`), must be an image by type and bytes, and is stored only through `upload()` (`partner-art.test.ts`).
- Only a resident's own agent link ask is ever finished: never link from a card alone.
- Anything X sends is untrusted. Store only the handle and the post link; never store, log, or show its HTML.
- What we tell musegod.org says only where a muse is and what it did, never anything about its holder, and no answer waits on a report. The discovery log counts start-file reads by partner and records nothing about the reader.
- Uploads are hostile bytes. A parser for an upload format reads every length unsigned (`|` and `<<` are signed, so a 32-bit length ends in `>>> 0` or is read with a `DataView`), checks it against its parent before using it, never allocates from an unchecked length, caps how many items it records and holds no object per item it only copies, keeps its work linear in the file's size, refuses rather than throws, and gets a truncation and random-corruption test plus a cap-sized hostile file (`strip-metadata.test.ts`, `image-size.test.ts`, `passkeys.test.ts`). Uploads are parsed in the World object, so a blowup resets the world for everyone. Removed metadata is overwritten in place with padding, so media data and its offsets stay put ([decision 0043](../../docs/knowledge/decisions/0043-strip-video-and-model-metadata-in-place-and-refuse-what-can-.md)).
- Image sizes come only from `probeImage` in `packages/cards/src/images.ts`, the one header reader. What counts as metadata in a JPEG, PNG, or WebP is one set of lists (`image-metadata.ts`) that uploads and model textures both read; `strip-metadata.test.ts` runs every entry through both.
- `make_piece` takes only the actor's own upload.

### Money and telemetry

- Caps that guard money ship with a test that proves they refuse (see "upload cost guards" in `social.test.ts`). The last test in front of a guard is never deleted.
- Triage spends money. Every call goes through `TriageClient.classify()`, which checks the key, the daily call and token caps, the share kept for reports, and the breaker before it fetches; `SafetyService` takes a slot (`takeTrigger`) first. A new path to the model goes through it, and its test proves it refuses at the caps (`triage.test.ts`). Never log the text sent or the key.
- Townsfolk chatter spends money and writes as residents. Every call (scheduled turn or mention answer) goes through `reserve` in `chatter.ts`, which checks the key, the breaker, and the daily call, token, and dollar caps before it fetches, reserving `worstCostMicroUsd` and settling to the cost. Chatter never sends `fallbacks`, so no call costs more than it reserved, and `answer` checks the day again right before it acts. The model names a post or resident only by a ref from lists the service built; `checkAnswer`, a `Moderation` with no townsfolk privilege, and `createPost` check the words. A mention's words reach the model only inside the untrusted block. A giver's job words come from the board. `chatter.test.ts` proves each cap and mention guard refuses. Never log the text sent, the text written, or the key.
- Every AI call writes a ledger row through `AiSpend.record()` (`ai-spend.ts`): purpose, trigger code, model, token counts, cost from `PRICES`, outcome. Never text or a resident id. A refused call writes none, and no guard reads the ledger. A new model needs a `PRICES` row first.
- Code names a model tier, never a model id. `MODELS` in `models.ts` maps `opus`, `sonnet`, and `haiku`, and `capabilitiesOf` says what each model takes, so a request never sends a field a model refuses. Moving a tier is its `MODELS` line, a capability row, and a `PRICES` row.
- Telemetry gets templates and codes. Spans, breadcrumbs, metrics, and reports go through `telemetry.ts` and carry route templates, route ids, status and error codes, and sim command types. Never an id, handle, token, key, code, IP, or resident text, even though the scrubber would catch most. Logs from the background runs (lessons, tips, welcomes, routines) carry counts and codes too. An error you catch and answer with `internal` also gets `report(err, where)`.

### Pictures

- Cards, plot photos, and pictures by link are drawn in the Worker, never in the World object. The World object calls the Worker's `PlotPhotos` entrypoint and its `picture` RPC answers with data only; the drawing happens in the cards Worker over the `CARDS` service binding ([decision 0299](../../docs/knowledge/decisions/0299-card-drawing-moves-to-a-worker-of-its-own-reached-over-a-ser.md)). Nothing here imports `@terrakin/cards/worker`, since its wasm would slow this Worker's every cold start. Build the `Card` here, call `env.CARDS.render`, and keep the caches and caps here.
- Public pictures cost CPU, so they're capped. A picture by link is asked of the world only past `allowPicture` (per IP), and drawn only with room in `allowRender` (per IP, looked at first, spent last) and `allowDraw` (all clients, per isolate or process); over any of them it gets the static card. `Cache-Status` says whether this answer drew it (`PICTURE_CACHE_STATUS`), made per answer and never cached. Nothing forces a draw past the caps. An unknown id is remembered `MISSING_TTL` seconds. Pictures show no uploaded art but a plot's home picture, only through `artShown`, so a purge changes the key; a look never shows an uploaded pattern tile. `pictures.test.ts` proves each cap and the art rule.
- `takePlotPhoto` runs the cost guards (the `photos` and `photosIp` limits, upload caps with room for a photo, per-IP bytes, two in flight) before drawing, and stores the PNG through `upload()`. `plot-photo.test.ts` proves each guard refuses before anything is drawn.
- Scene photos ([RFC 0049](../../docs/rfcs/0049-scene-photos.md)) need the `scenePhotos` option (`TERRAKIN_SCENE_PHOTOS=on`, set in `wrangler.jsonc` and by `pnpm dev:test` and the e2e servers); without it, `POST /v1/photos` and its reads answer 404. `ScenePhotoDesk` (`src/scene-photo-desk.ts`) runs every guard before a browser opens: the per-IP limit, the subject's checks (`sceneFor` in `src/scene-photos.ts`), the resident's 6 a day, the upload caps, one of the town's 100 renders for the UTC day (`ScenePhotoBook`, social database), then one of two at once. A failed render gives its slot back but counts toward 20 failures a UTC day, past which no browser opens until midnight, and a render's place among the two is held until its browser is really done, even after the desk stops waiting. The resident's day and a moment are taken with the town's slot and given back if no photo comes of it. Only the error's kind is reported, since a browser's message carries the ticket. The subject's scene reads the world's clock (`service.now()`), never the Api's. The browser runs in the cards Worker on Cloudflare ([decision 0382](../../docs/knowledge/decisions/0382-scene-photos-are-drawn-by-browser-run-in-the-cards-worker-on.md)) and in Playwright's Chromium on Node (`src/scene-renderer-node.ts`), and loads only the site's own origin. `scene-photos.test.ts` proves render 101 is refused before any browser opens.
- A plot photo draws a neighbor's work but never counts it. The photo story's mark is kept only once the photo is stored.

### By system

- Check-in (`checkin.ts`):
  - `todo` lines follow the `TODO` order, first-visit lines first and today's suggestion last, held by the test "puts first-visit steps first and today's suggestion last".
  - A step added later gets its day in `STEPS_ADDED`, or it lands in every resident's first visit.
  - An answer with a first-visit step or a suggestion is never `unchanged`, and a later step's suggestion never turns a quiet check-in into a full one.
  - It never suggests filing a proposal. `firstVisitView` records nothing. The shut-home line names the cheapest block that frees the resident.
  - Staff totals never show one resident's check-in times (`checkin-log.ts`). The newcomer funnel is counts only, never an id or name, with townsfolk left out.
- Names: `createResident` refuses the sim's `nameProblem` and a name taken by `nameKey`, offering `freeNames`.
- Praise and pet pats: once a UTC day per pair, with daily caps. Karma is scored once a UTC day, and a household never counts for itself.
- Together: putter and routine waves carry no note and never move a streak. A gift with a thing is `checkGesture`, `give`, then `sendGesture`.
- Routines: townsfolk routines never pause.
- Town Hall: `you.away` is set for filing, never for voting.
- Levels: `open_levels` waits until the collection book's backfill is wired, and `credit_event` goes through `creditOrWait`.
- Plot market: the seller's notice never names the buyer.
- Market: `listingRefusal` is the gate the sim can't check (time and karma).
- Events: sampling runs in the minute sweep, never a boot or a request. `event_started` and `event_soon` go once each, never to the host, townsfolk, or anyone blocked with the host. A void is refused for the host's household. Presents list who from, never what, and a wrapped `give` refuses a note.
- Games: `tableView` shows a viewer only their own sealed choice, the snapshot's `tables` never carries the play, and `townsfolkMove` is checkable from the salt once `game_over` shows it.
- Townsfolk: tips stop rather than pass a newcomer over on a refusal about the giver or the server (`STOP_CODES`), and `welcomeNow` gives one only when the daily run would. A welcome row is marked done before it's tried, one per resident ever.

## Where things are

Paths are under `src/` unless they say otherwise. Grep for the rest.

- `api.ts` the dispatcher (match, auth, rate limit, parse); `api-response.ts` replies as HTTP; `api-wiring.ts` joins world and social at start (`wireSocial`).

## Testing

`src/server.test.ts` starts a real server on port 0 and talks to it over `fetch` and `ws`. Every new route or message type gets an integration test. Use `MemoryStore` unless you're testing persistence. Pass `onResponse` from `responseChecker()` (`src/test-support.ts`) to every test server; it fails the suite on a response that doesn't match the route table. Use `listenOnFreePort` (127.0.0.1 only, never every address) and `jsonCaller` from there instead of writing another.

The server project runs with `isolate: false` (`vitest.config.ts`): a test file never swaps a module with `vi.mock` and puts back any global it changes. To see what `report` and `gauge` send, use `recordTelemetry()` from `src/test-support.ts`, with `start` before each test and `stop` after.

## Writing tests

A test here answers the four questions in the root [definition of done](../../AGENTS.md#definition-of-done) first. A near-copy here usually means a second server: extend the test that owns the contract instead.

The HTTP route test owns a route's contract. A unit test of a helper behind the route earns its place only with cases the route can't reach cheaply. Every cap that guards money keeps a test that fails when the cap is bypassed. Resident text in a test never holds a random id: the filters fold leetspeak, so an id holding `a55` reads as strong language and the test fails now and then.
