# packages/sim/

The rules engine. If a rule decides what's allowed in the world, it lives here and nowhere else.

## Invariants (tests enforce these; don't weaken them)

- **Pure and deterministic.** No `Date`, `Math.random`, timers, network, filesystem, or host globals. The tsconfig has no DOM or Node types on purpose. If you need randomness, add a seeded RNG to `WorldState` and draw from it.
- **Check, then commit.** `prepare()` runs every check and mutates nothing; its `commit()` makes the change. `apply()` is both in one call. A rejected input leaves state byte-identical (`hashWorld` before == after). The server persists between the two steps.
- **`seq` goes up by exactly one per accepted input.**
- **Events describe every change.** Clients mirror the world from events alone, without re-running rules. If you change state, emit an event for it.
- **State is plain JSON data.** Records, arrays, numbers, strings. No `Map`, classes, or `undefined` values, so `canonicalJson`/`hashWorld`/`cloneWorld` stay exact.
- **Replay must reproduce.** An accepted log replays to the same hash forever. Changing a rule that would change how existing logs replay needs an RFC ([decision 0003](../../docs/knowledge/decisions/0003-deterministic-sim-with-input-log.md)) and a bump of `REPLAY_VERSION` (`src/replay.ts`), since the server boots from snapshots and no longer re-runs old inputs ([decision 0070](../../docs/knowledge/decisions/0070-replay-version-marks-rule-changes-that-make-old-snapshots-un.md)).
- **A snapshot plus the rest of the log is a straight replay.** A world written with `JSON.stringify` and read back with `JSON.parse` must apply the inputs after it to the same hash and the same event bytes. `replay.test.ts` checks every split point of every log in `src/fixtures/`, so a new fixture is covered by adding the file. Rules may not depend on anything outside the state.
- **Ids from inputs are own keys.** Look a record up by an id from a command with `own(record, id)` or `residentById(state, id)` (`src/own.ts`), never `record[id]` or `id in record`: `__proto__`, `constructor`, or `toString` would find what every object inherits, and since inputs are logged, the damage would replay on every restart. Write under such an id only after it was found, or after `isOwnableKey`. `own.test.ts` throws those ids at every input that takes one.
- **A rename keeps the old name replayable.** A command or field the sim renames keeps its old name in `src/renamed.ts`, which `prepare` reads every input through (`currentCommand`), so a log that holds it replays as it was made; the API refuses the old name. `add_storey` and `storey` (decision 0252) are there ([decision 0271](../../docs/knowledge/decisions/0271-a-renamed-command-or-field-keeps-its-old-name-in-the-sim-so-.md)), and every kindred command with the `kindred` field and the `k_1` ids it carried (decision 0318), and `floors.test.ts` and `circles.test.ts` replay their logs under them. A logged command no rule knows throws, naming its type and `seq`, rather than building a different world.
- **New state is absent until used.** A new field stays off old records until an input sets it, and bookkeeping without an event starts only after a new input (like the first `new_day`), so old logs keep their hash. `src/fixtures/pre-town-log.ts` pins one such hash.

One more rule, which no test enforces: the package is **free of side effects**. `package.json` says `"sideEffects": false`, so the web client's bundle leaves out the sim modules it doesn't use ([decision 0258](../../docs/knowledge/decisions/0258-the-first-load-s-budget-is-135-kb-counted-as-it-is-downloade.md)). A module may build its own tables when it loads (`CATALOG`, `SHOP_CATALOG`), but must never do something at import time that another module relies on without importing a name from it: no registering into, filling, or freezing a table another module owns, and no `import "./x"` for effect.

## Where things are

- `src/types.ts` world, command, event, and rejection types. Start here.
- `src/apply.ts` the rules. One `case` per command.
- `src/world.ts` geometry helpers and `DEFAULT_CONFIG`, with where the Town Hall, the shop, and the game tables stand (`townHallTiles`, `shopTiles`, `gameTableTiles`), and `settleProblem`, why `settle` would turn a plot down, which `settle` checks with and the web's plot picker reads. **`downtown(state)` is the rectangle the world had before any land opened** (`state.lands.home`), and every rule about the town's centre reads it rather than `state.config`, which `open_land` grows: `commonsPlot`, `isCommons`, `spawnTile`, the buildings and the table spots all take the world for that reason, so passing the grown config is a type error rather than a town that drifts east ([decision 0326](../../docs/knowledge/decisions/0326-an-island-is-a-region-of-the-same-plane-and-water-is-what-is.md)). The buildings are laid out one square at a time (`Square`, `squares`, `hallDoor`, `hallTiles`, `counterDoor`, `counterTiles`, and `squareOf` for a reader that has the tiles and not the world): downtown's square is the Commons, every open land brings one of its own, `isTownSquare` is the question `settle` and `claim` ask of a slot nobody can claim, and `src/doors.ts` says which counter or green a resident is sent to ([decision 0332](../../docs/knowledge/decisions/0332-every-island-gets-a-counter-and-a-hall-door-of-its-own-on-a-.md)). An island's hall building stands on its square and takes no filings: `townHallTile` is downtown's door, the only one `propose` measures to ([decision 0353](../../docs/knowledge/decisions/0353-an-island-s-hall-building-stays-standing-and-takes-no-filing.md)). `settleProblem` takes `square` as a required fact for the same reason. `outOfReachHere` in `src/floors.ts` is the one `out_of_reach` refusal for a tile more than a reach away: its caller's words (building's "You can only build within N tiles.", "That's more than N tiles away." for the rest) and then `walkWords`' walk on the floor the resident stands on, or that no walk gets there. Every refusal that ends in a walk says it through `walkOrWhy` in `src/walk.ts`: the lead sentence, then the walk, or the one sentence for when no walk gets there. Building and fireworks call it directly, and growing, making, gathering a tile, and showing through `reachProblem` in `items.ts`, which checks the tile is in the world first. No refusal names a straight line: one points through whatever stands between. `reach.test.ts` sends each such command from behind the starter hut, follows the refusal's walk move by move, and sends the command again, which must work; a new command that checks reach goes in its table.
- `src/walk.ts` walking ([decision 0072](../../docs/knowledge/decisions/0072-walking-is-eight-ways-around-solid-buildings-paced-by-your-f.md)): `stepFrom`, the one rule for a step (eight directions, never off the world, into a block, or onto a solid building, and never diagonally past a corner), checked for every `move` and putter step, and on a refusal it reports `at`, the tile it blamed, so a caller can say what to do about that tile; `walkLegsTo`, the walk a refusal names, around what's in the way, on the world's ground or a floor's own, and `walkWords`, the same as `move` calls, which every refusal for a place too far away ends with (the link pages make links from the legs); `groundOf` and `worldGround`, the ground a step reads on the ground floor, which the client builds from its mirror with the same function (upstairs, `floorGround` in `src/floors.ts`); `walkTree` and `route`, breadth-first walks over the same rule, for the putter planner and the client's tap-to-walk; and the server-only `solid_buildings` (`checkSolidBuildings`, from `TOWN_ACTOR`), which sets `state.solidBuildings` and steps anyone standing on the Town Hall or the shop off to the nearest open tile. Before it residents walked across both, so older logs replay as they were made. `src/fixtures/walk-log.ts` pins a log with diagonal steps and the switch.
- `src/hash.ts` canonical JSON + FNV-1a fingerprint. `src/keys.ts` the `"x,y"` record keys for tiles and plots.
- `src/replay.ts` rebuild state from a log, and `REPLAY_VERSION`, which the server stores with each world snapshot (RFC 0014).
- `src/presence.ts` presence that comes with acting (RFC 0014 step 4, [decision 0071](../../docs/knowledge/decisions/0071-presence-comes-with-acting-once-implicit-presence-is-logged.md)): `implicit_presence` turns it on (`state.implicitPresence`, absent until then) and `leave_idle {ids}` takes everyone in `ids` offline with a `left` each, both from `TOWN_ACTOR`. Once it's on, `prepare` brings a known, offline resident back for their own command (not `join` or `leave`) with `join`'s rules (`rejoined` in `apply.ts`), checking with them back in place and putting everything back before it returns; `commit` emits `joined` first. `asJoined` is the same as a read-only view, for planning walks and dry runs. `src/fixtures/presence-log.ts` pins a log that uses it.
- `src/routines.ts` offline routines ([RFC 0009](../../docs/rfcs/0009-offline-routines.md), [decision 0082](../../docs/knowledge/decisions/0082-routines-are-logged-steps-the-sim-checks-due-from-their-utc-.md)): `set_routines` (a resident's list in `state.routines`, at most one `walk_home`, `stroll`, and `greet`, in `ROUTINE_KINDS` order, absent until the first) and the server-only `routine_step {resident, routine, step}` from `TOWN_ACTOR`. A step is refused for a routine that isn't on (`not_set`), a resident who's online (`awake`), or one that used up its day (`ran_today`: `walk_home` once, a stroll `ROUTINES.strollTiles` tiles over its legs, kept in `state.routineRuns`), and then meets the resident's own checks: `home` (refused `already_home` even with the allowance due) or a putter's steps that must stay on plots they can build on. It's a server command, so it pays no allowance or pantry and never bumps `lastActiveDay`; its `moved` events carry `routine`. `planStroll` and `strollBack` are the server's planner, never replay's. `src/fixtures/routines-log.ts` pins a log that uses them.
- `src/town.ts` the Town Hall (RFC 0004): eligibility, proposals, votes, closes, builds, `TOWN_LIMITS`. A `commons_build` is `build`'s four lists at world tiles in the Commons: `COMMONS_BLOCKS` (the building blocks, decor, furniture, and `pond`) and any ground, 40 changes in all, checked whole when filed (`checkPlan`) and built at close in `build`'s order with what moved since skipped (`closeBuild`), from nobody's things ([decision 0101](../../docs/knowledge/decisions/0101-a-town-hall-build-lays-paths-and-places-decor-and-furniture-.md)). `checkPropose` hands its plan to `prepare`, so a dry proposal previews it. Once the server logs `keep_table_spots` (`checkKeepTableSpots`, from `TOWN_ACTOR`; it sets `state.tableSpotsKept`), a build puts no block on a game table's spot (`gameTableTiles`): filing refuses one and closing skips it, while paths and removals still go there ([decision 0126](../../docs/knowledge/decisions/0126-town-hall-builds-keep-the-game-tables-spots-clear-from-a-log.md)). Before it, blocks went on the spots, and older builds replay that way. Once the server logs `propose_in_person` (`state.proposeInPerson`, [RFC 0042](../../docs/rfcs/0042-actions-that-need-you-there.md)), `propose` needs the actor at downtown's Town Hall door (`townHallTile`), by `notAtTheHall`, from whatever land they stand on, since filing stays downtown ([decision 0352](../../docs/knowledge/decisions/0352-an-island-s-presence-is-its-shop-counter-town-hall-filing-stays.md)), and once a land is open its words say "the Town Hall downtown"; `vote` is untouched and stays callable from anywhere, because a proposal closes on a clock. The flag is top level rather than on `TownState`, which the first proposal creates lazily. `src/doors.ts` holds `notAtDoor`, the one check behind every action RFC 0042 moves onto the map, and `nearestCounter` and `nearestPark`, which counter or green a resident is sent to now that every land has one: the square of the land they stand on, the nearest of those when a land has more than one, and the nearest of all from a bridge tile, by reach's own distance with ties north to south then west to east. The land comes before the distance because crossing the water means walking to the bridge, which is far longer than the crow flies ([decision 0332](../../docs/knowledge/decisions/0332-every-island-gets-a-counter-and-a-hall-door-of-its-own-on-a-.md)). Every rule and view asks through those, and the resident is never told which door they got: the refusal names the walk to it. The hall is not among them: `notAtTheHall` and the server's `you.hall` read `townHallTile`. Commands the server sends itself (`new_day`, `set_townsfolk`, `close_proposal`, `void_proposal`) must come from `TOWN_ACTOR` ([decision 0026](../../docs/knowledge/decisions/0026-time-enters-the-sim-as-logged-day-and-close-inputs.md)).
- `src/looks.ts` the looks catalog (RFC 0005): themes, patterns (the nine geometrics and then `PRINTS`, the eight that scatter one named thing, [decision 0328](../../docs/knowledge/decisions/0328-prints-are-drawn-motifs-from-the-catalog-because-a-card-cann.md); a new print goes on the end of `PRINTS` and so on the end of `PATTERNS`, so older wear lists and garment styles hash the same), wear and its five slots (a dress covers the bottom slot), `wearStyle`, a pattern and color per garment merged item by item ([decision 0053](../../docs/knowledge/decisions/0053-any-garment-can-carry-its-own-pattern-and-color-with-bottoms.md)), and hair: `HAIR_STYLES` and `HAIR_COLORS` with their labels and colors, two look fields that `null` clears, the color kept while there's no style ([decision 0074](../../docs/knowledge/decisions/0074-hair-is-a-style-and-a-color-on-the-look-drawn-under-hats-in-.md)). New slots go on the end of `WEAR_SLOTS`, so older wear lists sort the same. `EARNED_WEAR` (RFC 0029) is the five garments a skill's level 5 unlocks. They're in `WEAR_ITEMS` and `WEAR_INFO` like any wear, before partner wear, so whatever lists wear for everyone (the collection book, a newcomer's tops, the look editor) leaves them out with `isEarnedWear`. `JOB_WEAR` (RFC 0030) is the town satchel that jobs finished bring, after them in both tables and left out the same way with `isJobWear`. The protocol and client import it.
- `src/putter.ts` `planPutter`: where a `putter` walks (up to `PUTTER.steps` steps over `walkTree`, diagonals too, next to someone nearby, else a neighbor's plot or your own plot's edge, else the Commons, else anywhere open), with choices picked by a hash of the actor, `seq`, and `day`. The server calls it and logs the steps; the sim checks them like moves, so replay never runs the planner and tuning it never changes old logs. `PUTTER_MAX_STEPS`, the sim's cap on logged steps (`too_far` past it, for a putter and a routine's stroll alike), may go up but never down ([decision 0049](../../docs/knowledge/decisions/0049-putter-is-a-planned-short-walk-logged-as-its-steps-with-a-on.md)).
- `src/visit.ts` `visit {px, py}` (RFC 0020, [decision 0091](../../docs/knowledge/decisions/0091-visit-is-a-jump-to-a-neighbor-s-door-logged-with-the-tile-th.md)): `visitTile`, where a visitor lands (a free tile on the plot's outermost ring, on a path if one meets the edge, with the shortest walk to its heart, `plotHeart`: its owner's hearth, else a co-owner's, else its center, so in front of a hut's doorway), which the server calls and logs with the command; and `checkVisit`, which checks the logged tile and never runs the planner, so a better planner never changes how a logged visit replays. `src/fixtures/visit-log.ts` pins a log of visits. `plotDistance` in `src/world.ts` is how far a tile is from a plot; the server's plot admires read it.
- `src/plot-names.ts` plot names ([decision 0121](../../docs/knowledge/decisions/0121-a-plot-s-name-lives-on-the-plot-in-the-sim-set-by-its-reside.md)): `PLOT_NAMES` (the longest name, and `freeRenames`), `name_plot {px, py, name}` from a plot's owner or a co-owner, from anywhere, and the server-only `clear_plot_name {px, py}` from `TOWN_ACTOR` (staff, after a report). A name sits on the plot as `name`, with `namedBy` and `namedDay`, all absent until the first. It changes once a world day (`rename_limit`), and a change on a day it already changed takes one of the plot's two free renames while a name is up (`freeRenamesUsed`, absent until the first; `freeRenamesLeft` reads it, and `plot_named` carries it after one). The limit refused every such change before, so no logged name used one and old logs hash as they did. `null` clears it any time and keeps `namedDay`, so clearing (or a takedown) never makes room for another name that day. `release` drops the plot's record, so the name and its free renames go with it. `plotNamesOf` lists the names a resident answers for (plots they own, names they wrote) for reports. `homePlotOf` in `src/world.ts` is the plot a resident calls home. `src/fixtures/plot-names-log.ts` pins a log that names, clears, takes down, releases, and renames, and `src/fixtures/free-renames-log.ts` free renames on top of it.
- `src/lands.ts` new lands beyond the first grid ([RFC 0038](../../docs/rfcs/0038-new-lands.md)): `LANDS` (every number), the server-only `open_land {land, name, width, height, plots, bridge}` from `TOWN_ACTOR`, once per land id, which grows `config.width` and `config.height` to the numbers it carries and records the land in `state.lands` (absent until the first; `home` is the rectangle the world had before, so downtown needs no slot list), and the read helpers `onLand`, `landOfPlot`, `landOfSquare`, `onBridge`, `isSea`, `seaFrom`, `landPlots`, `plotsLeft`, `landName`, and `squareWords`. An island is a region of the same coordinate plane, not a world of its own, so `tileKey`, `biomeAt`, `move`, `visit`, `putter` and the routines need no change. **Water is what's left**: a tile in bounds on no land's plots and not a bridge tile is sea, which `groundOf` takes as the `sea` obstacle, `settle` and `claim` both refuse (`plot_is_water`, answered with `out_of_bounds`, since either way the next move is another plot; `claim` reads the slot a resident stands on, and a bridge tile is in a water slot), `pickupOn` leaves bare, so no branch, stone, or find lies on it, and `isWater` in `fishing.ts` casts into (decision 0339). That last one is a rule change, and what makes it safe is that no log holds an `open_land` and a gather near water: `gather` reaches `config.reach`, not just the tile underfoot, so in a world that already had a land open someone on the shore could have taken a sea tile before it. No world has opened one. `seaFrom(config, lands)` is that one rule, built from the facts the world snapshot carries rather than from state, so the web answers it as the rules do and a world with no lands is handed no `sea` at all; `isSea` and `worldGround` read it. `plotsLeft` counts the slots anyone could still claim, which is what the server watches to decide when to open the next land (`LANDS.openAt`); no rule here reads it, and it takes the Commons from `lands.home` rather than the grown config. Everything geometric arrives in the logged input, so the rules never work any of it out and a better planner can't change how a logged input replays. Before the first `open_land` there is no sea, because every tile in bounds is downtown, so older logs walk and settle exactly as they did. **A land also brings a square**, the one plot slot in `square` that its own shop counter and a hall building stand on ([decision 0332](../../docs/knowledge/decisions/0332-every-island-gets-a-counter-and-a-hall-door-of-its-own-on-a-.md)): `landedFrom` counts it, so it is ground rather than sea on the wire as in the sim, `landPlots` leaves it out, so it never counts toward the plots left to claim, and `settle` and `claim` refuse it with the Commons' own code and words that name the land (`squareWords`). It is logged rather than worked out, so a better planner can place the next land's square differently without changing how this one replays, and `open_land` refuses one outside the world it makes, on land already, among its own plots, under its bridge, touching the land only at a corner (where no walk would reach its buildings), or touching anything else (where it would be a dry crossing of its own). `src/fixtures/lands-log.ts` pins a log that opens a land, settles across the water, and walks the bridge a tile at a time, and its `LANDS_ISLAND` is the one island every test that needs a land open sends. **A land may bring streets** ([RFC 0046](../../docs/rfcs/0046-streets.md), [decision 0356](../../docs/knowledge/decisions/0356-new-lands-are-laid-out-with-streets-logged-in-open-land-and-.md)): `open_land`'s optional `streets`, whole plot slots kept on the land as `streets` (absent on a land with none, so older logs hash as they did). `landedFrom` counts them as land, `landPlots` and `plotsLeft` leave them out, `isStreet` asks, `landOfSlot` is the land of any of its slots (plot, square or street), which `doors.ts` reads, and `settle` and `claim` refuse one with `public_ground` and `streetWords`, naming the nearest free plot (`settleProblem`'s required `street` fact, `plot_is_street`). `nearestFreePlot` skips them. `open_land` holds a street to a plot slot's rules, and the square must touch its plots or its streets side on, since the long cross puts it where streets cross. Nothing can be built on one, since it is nobody's: `place`, `remove`, `lay`, `lift` and `build` refuse it with `public_ground` too. `openings.ts` counts it as open ground like any unclaimed slot. `src/fixtures/streets-log.ts` opens a small long cross, claims every plot, and walks from a plot to the counter and the bridge on streets alone; `streets.test.ts` pins it.
- `src/ways.ts` public ways ([RFC 0046](../../docs/rfcs/0046-streets.md), [decision 0358](../../docs/knowledge/decisions/0358-a-public-way-is-tiles-of-a-plot-that-hold-no-block-laid-by-t.md)): `state.ways` (tile keys, absent until the first), the server-only `open_way {tiles}` and `close_way {tiles}` from `TOWN_ACTOR`, `isWay`, and `wayProblem`, the `public_ground` refusal `place` and `build` (whole plan) ask before a block goes on the ground floor of a way tile. `build_starter_home` skips a way tile as it skips a block already there; it used to refuse the whole hut, so no logged one met a way and they replay as they were built. `open_way` is refused on a block, a hearth, a square or street, water, and a listed plot, so the town clears a tile first with `clear_block`. `src/rebuild-home.ts` is the server-only `rebuild_home {px, py, blocks, remove}`: a `build` as the plot's owner, with a public `home_rebuilt`, which the town uses to close a home a way cut through. `openings.ts` counts a step onto a way as open ground (`OpeningFacts.way`), but only a way a walk from the Commons reaches over unclaimed ground and ways (`joinedWays`), so a stray way that leads nowhere is no exit. `claimNotes` in `design.ts` adds `way_tiles` for a slot a way crosses. Once the server logs `open_way_pickups` (`checkOpenWayPickups` in `gather.ts`, from `TOWN_ACTOR`; it sets `items.wayPickups`), a way's pickups are anyone's under `own_plot_pickups` (`mayGatherOn`'s `onOpenWay`, `mayGatherAt`). It is a switch because a `gather` with no tile would otherwise take more on replay than it took when it was logged. The words: a **street** is an island slot nobody owns, a **public way** a downtown tile that holds no block, an **exit** a plot's way out, and **open ground** where an exit lands; in code, "way" means only a public way. `rebuild_home` builds from the owner's things and relies on the server planning only free walls and a door. `src/fixtures/ways-log.ts` pins a log that clears a hut's wall, lays a way through it, rebuilds the home with a door and walks out; `ways.test.ts` pins it and every refusal.
- `src/biome.ts` `biomeAt`: the ground biome of a tile (one of `BIOMES`), a pure function of its position. Never state, never in the log ([decision 0045](../../docs/knowledge/decisions/0045-biomes-are-a-pure-function-of-position-presentation-only.md)). Gathering reads it, so changing the map changes replay and needs an RFC. `biome.test.ts` pins the map.
- `src/season.ts` `seasonOf`: the season of a world day (spring is March to May, summer June to August, autumn September to November, winter December to February, by the UTC calendar), with `seasonSpan` for where it starts and ends and `dateOfDay`/`dayOfDate` for the calendar. A pure function of `state.day` like `biomeAt` is of position: never state, never in the log. A rule that reads it changes with the calendar, so pin it in a test. The shop reads it for seasonal stock and buying (RFC 0017, below). `weekStart` is the Monday of a world day's UTC week, which the rated-game and bounty weeks share.
- `src/holiday.ts` holidays ([RFC 0022](../../docs/rfcs/0022-holidays.md), [RFC 0034](../../docs/rfcs/0034-winter-holidays.md), [decision 0106](../../docs/knowledge/decisions/0106-holidays-are-dated-windows-read-from-the-world-s-day-candy-i.md)): each one in `HOLIDAYS` has a span rule in `HOLIDAY_INFO` (`HolidaySpan`): fixed dates (Halloween is October 24 to November 1, Midwinter December 21 to 31, New Year's December 26 to January 1, Thanksgiving the fourth Thursday of November with its days either side, and Hanukkah eight days from a table of first-candle dates that `hanukkah.test.ts` holds three years ahead of the clock), the nth weekday of a month with days either side, or a table of first dates and a length. `spanIn` reads a rule for a year, `holidaySpan` a holiday's run that starts in a year (none when a table lacks it), and `holidayRun`, `inHoliday`, `nextHolidayStart`, and `holidayLastDay` read the run around a day. A run may cross into the next year, and two holidays may run on one day, so a rule asks `inHoliday` about its own and `holidaysOf` lists them all. `weekdayOf` is a day's weekday (0 is Sunday), and `hanukkahNight` which night of Hanukkah a day is, for the menorah's candles. A pure function of `state.day` like the season: never state, never in the log. `holidaysField` is the `holidays` field the world snapshot and the check-in carry. New holidays go on the end of `HOLIDAYS`, and the jobs board walks every holiday's edges (`nextEdge` in `jobs.ts`), so `jobs.test.ts` pins that a new one moves no logged day's board.
- `src/weather.ts` `weatherAt`: the weather of a world day and UTC hour (`clear`, `cloudy`, `rain`, `fog`, `snow`), in spells of 3 to 6 hours per day (`weatherSpells`) drawn from each season's `WEATHER_CHANCES`, snow only in winter, and `skyAt`, the weather and season at a moment on a clock, which the server and clients both use, and which the server logs with each `fish` (the only rule that reads the weather, from that logged copy) ([decision 0073](../../docs/knowledge/decisions/0073-weather-is-a-pure-function-of-the-world-day-and-the-utc-hour.md)). ## Items

- Nothing about items runs until `open_items`, which creates `state.items`. Until then old logs replay exactly; `src/fixtures/items-log.ts` pins a log with crops, crafting, and gifts on top of the post-economy one.
- Growth reads only `state.day`: a crop stores `plantedDay` and `readyDay` and is ready once the day reaches `readyDay`. `new_day` changes nothing about crops (it resets the daily counters), so a skipped day counts like any other and there is nothing to replay per crop.
- The pantry is bookkeeping in `prepare()`'s commit, like the allowance: it pays when a resident's own input leaves them on their hearth, once a day, only when it has something to add (so it never changes state without an event), and never to townsfolk. The first one brings the starter seeds. `home` while already home is accepted when the allowance or the pantry is due.
- The first pantry gives `STARTER_SEEDS`, never every kind in `SEED_KINDS`, and every pantry tops up `PANTRY_STAPLES`, never every staple: both are frozen, so a new seed or staple (like autumn's `pumpkin_seed`) never changes what an old pantry gave. The items log's hash and `catalog.test.ts` pin them.
- `craft` takes any recipe in `GOOD_KINDS`, `FURNITURE_KINDS`, or `SWEET_KINDS`, family recipes' kinds included. A sweet stacks like furniture and takes no label, and its recipe can make more than it uses (`makes`: five candies from a pumpkin and a bag of sugar, five candy canes from a bunch of herbs and a bag of sugar), so only such a craft checks for room (`inventory_full`). Asked for a family recipe's name with a kind outside its family (`tomato_jam`), it names the kinds the recipe takes.
- Seeds, produce, and staples stack as counts (absent at 0). A made thing has an id from `items.nextId`, its maker, and its made day, and keeps them wherever it goes. Every unit counts toward `inventoryMax`.
- Inventories are private, like purses. An `inventory` event belongs to its `residentId` alone; a gift makes two. `planted`, `harvested`, `gathered`, and `item_given` (no count, no note) are public. Use `inventoryOf` for `GET /v1/inventory`.
- A planter with a crop in it can't be removed. Anyone who can build on the plot may harvest it into their own inventory.
- Pieces (`PIECE_KINDS`) are made things with no recipe, so they're not in `GOOD_KINDS`; use `MADE_KINDS` and `isMadeKind` for "its own item with an id". Displays live in `items.displays`, absent until the first `display`; a displayed thing stays its displayer's (`by`), `take_down` returns it to them (or, when someone else takes it down and they're full, holds it aside), and a pedestal or frame with something on it can't be removed. `remove_display` (staff, after a report) returns it too, or, when their things are full, puts it in `items.heldAside` (absent until the first), and `returnHeldAside` gives it back in `prepare()`'s commit with their first input that leaves room. With `picture`, it drops `media` and `model` from every piece showing that upload, wherever it is.
- Gifts can be sent back once the server logs `open_gifts`, which creates `items.gifts`. From then on each accepted `give` records a gift (`gift_1`, ...) that its recipient may send back whole with `decline_gift` until `lastDeclineDay`, if the giver has room. `new_day` forgets older ones. Before `open_gifts`, `give` hashes exactly as it did ([decision 0057](../../docs/knowledge/decisions/0057-a-gift-can-carry-a-thing-and-its-recipient-can-send-it-back-.md)).

## Recipes (RFC 0024)

- Nothing about recipes runs until `open_recipes`, which needs the shop open and creates `state.recipes` with every resident in the world then in `everything`, sorted. Until then `knows` says yes to everyone, `pick_recipe` and `teach` are refused (`already_known`), a `recipe:` sku is an unknown sku, and no find is a page, so old logs replay exactly; `src/fixtures/recipes-log.ts` pins a log with recipes open, and `src/fixtures/lessons-log.ts` one with lessons, a townsfolk's lesson, and a recipe page.
- A resident knows `BASE_RECIPES`, every holiday recipe, what's in `learned` for them, and everything when they're townsfolk or in `everything`. A recipe added to the catalog later is a card unless it's in the base or has a holiday, and `everything` covers it too. The base is frozen: a new base recipe needs a logged input of its own.
- `craft` checks `knows` (`recipeUnknown`, called from `apply.ts`) after every check of its own and before it takes anything, and refuses with `recipe_unknown`, naming a free pick while one is left, the card's price and sku, a neighbor's lesson, and the recipe's page.
- `pick_recipe` takes a card on today's shelf (seasonal cards only in their season, like the shop's seasonal stock), up to `RECIPES_RULES.starterPicks`; known is `already_known`, used up is `no_picks_left`, which names the card's price and sku, and for a seasonal card off the shelf when it's back. Residents who know everything have no picks.
- A card is `shop_buy` with sku `recipe:<name>` and no count but 1, routed to `checkBuyCard` once recipes are open. It meets the shop's checks (`opened` in `shop.ts`: open, joined, not townsfolk), then known (`already_known`), the shelf (`out_of_season`), and coins (`not_enough_coins`), and splits like any purchase: the treasury's share, the rest burned. Cards aren't things: nothing goes in an inventory, so nothing can be given, sold, or listed.
- `teach {recipe, to}` (`checkTeach`): a recipe the teacher knows (`recipe_unknown`), not the base or a holiday's and not one the learner knows (`already_known`, also for yourself), to a resident who's online (`not_joined`, `unknown_resident`) and within `config.reach` (`out_of_reach`, with the routed walk). Each resident teaches `RECIPES_RULES.teachPerDay` and is taught `taughtPerDay` a UTC day (`taught_today`), counted in `items.today.teaching` and `items.today.taught` (absent until the day's first lesson; `new_day` drops them with the rest of `today`). A townsfolk's lesson isn't counted against the townsfolk, and comes to each resident at most once in `townsfolkEveryDays` world days (`townsfolkTaught`, the world's day; `taught_today` too). Which townsfolk teaches what, and when, is the server's (its lessons run); the sim checks each lesson like any other. `teachable` is what one resident knows that another doesn't, past the base and holidays, for profiles.
- Recipe pages (`gather.ts`): once finds are out and recipes are learned (`pagesOpen`), a tile whose find roll lands on a find is a `recipe_page` instead when `pageOn(x, y, day)` says so: its own roll, about one in `RECIPES_RULES.pageOneIn`, each of the frozen `PAGE_RECIPES` as likely. Pages only stand where a find would, so no branch, stone, or other tile moves. Gathering one teaches its recipe (`how: "found"`) and puts nothing in your things, so it needs no room; one you know is refused as `already_known` and stays. `gather` with no tile takes each page for a recipe you don't know (one page a recipe) after its stacks, ends in a `recipe_learned` per page after the `inventory`, and refuses `already_known` when a known page is all that's within reach. `pageKnown` says whether a pickup is a page the resident knows; `nearestOpenPickup` passes those over, and clients and the gather link call it to leave them out of what they count. `PAGE_RECIPES` is frozen like `FIND_SPAWNS`: a new card is no page until a new list starts at a logged switch.
- Every way to learn ends in a private `recipe_learned` (`how`: `picked`, `bought` with `price`, `taught` with `from`, or `found`). The server sends it only to its resident, and a lesson's to its teacher too.
- Card prices come from `recipeCardPrice`, never a table; `recipes.test.ts` pins every one and checks each card for a good the town buys pays back in 5 to 30 days of selling. Once recipes are open in a live world, changing a number in it, or a lesson limit, or `pageOneIn`, changes how logged inputs replay, so it needs a logged switch. `recipes.test.ts` pins the page count over four weeks of the real world's size.

## Building (RFC 0016)

- Paths and flooring live in `state.ground` (tile key to kind), absent until the first `lay` or `build` lays one. Ground never blocks: `isSolid` reads blocks only. It goes under blocks, hearths, and anyone standing there. `release` refuses (`plot_has_blocks`) while a plot has ground, as it does with blocks.
- A ground kind with a cost takes it from the layer's things and gives it back to whoever lifts it, like decor. Free kinds touch nobody's things and work before items open.
- Furniture (`FURNITURE_BLOCKS` in `types.ts`, the catalog's `furniture` role) is a block kind and a stack kind, held and placed like decor (`isHeldBlock`), and every piece blocks walking but the seats in `WALKED_ONTO_SEATS` (RFC 0044). A new piece is a catalog entry with the role `furniture` in the decor › furniture family, and its name on the end of `BLOCK_KINDS`, never in `FREE_BLOCKS` or `BUILDING_BLOCKS`. It never becomes a good (a good is a made thing with an id and a maker, not a stack). A furniture craft takes no label and counts toward `craftPerDay`.
- `build` names a plot and counts tiles from its north-west corner. What the plan gets wrong refuses all of it; what moves (someone standing, a hearth, a tile already holding something) is skipped and reported. Removals and lifts go first and pay for what the plan places. Its events are the single actions' own plus one `inventory` (`built`) with the net change.
- `src/fixtures/build-log.ts` pins a log that gathers, makes furniture, places it, lays and lifts ground, and builds a plan, on top of the presence log.
- A `pond` (RFC 0023) is a block paid for in stone (`POND`), not a stack kind: `place` takes `POND.stone` from the digger's things and `remove` gives them to whoever takes it up. What any block costs is `blockNeeds` in `items.ts` (decor and furniture one of themselves, a pond its stone, stairs `FLOORS.stairsWood` wood, the rest nothing), which `place`, `remove`, `build`, and `build_starter_home` all read. A starter home is never built of it.
- A `door` (decision 0349) is a free block, not held and not in `FREE_BLOCKS` (so never a starter home's walls or windows) or `BUILDING_BLOCKS` (so no theme recolors it and the Town Hall doesn't place it), on the ground floor only (`ground_floor_only`), and, with stairs, one of the two blocks `blocksWalkers` lets anyone onto, so every walk goes through it. It holds nothing up. From the server's `starter_doors` on, `build_starter_home` puts one in the hut's doorway (`starterHome`'s `door`); before it the doorway stays open, so older starter homes replay as they were built and `REPLAY_VERSION` doesn't move. `src/fixtures/doors-log.ts` pins a log on each side of the switch, and `walk.test.ts` its hash and a hearth walled in but for a door walking out to the town. A lock, if one ever comes, opens for whoever the plot's owner allows and never counts against a plot's way in.
- A Town Hall `commons_build` lays and lifts ground and places decor, furniture, and ponds in the Commons from nobody's things, so it never touches an inventory and works before items open ([decision 0101](../../docs/knowledge/decisions/0101-a-town-hall-build-lays-paths-and-places-decor-and-furniture-.md)). Only proposals with paths carry `ground` and `lift`, and `town_built` has `laid` and `lifted` only when there are some, so older builds close with the events they always made. `src/fixtures/commons-log.ts` pins a log of Commons builds on top of the build log, and `src/fixtures/table-spots-log.ts` one on both sides of `keep_table_spots`.

## Floors (RFC 0028)

- A `floor` is a level of a home, always a number, and flooring is what's laid on a tile (a ground kind, `ground` in state and commands): the two words never stand for each other ([decision 0252](../../docs/knowledge/decisions/0252-a-home-s-levels-are-floors-in-the-api-and-an-upstairs-in-wha.md)). An input logged under the earlier names (`add_storey`, `storey`) reads as `add_floor` and `floor` through `src/renamed.ts`, with `storey: 0` as the ground floor; `floors.test.ts` holds it.
- The ground floor is floor 0 and stays in `state.blocks` and `state.ground`. Each floor above it is its own layer in `state.floors`, keyed by its number (`"1"`), with `blocks` and `ground` keyed by `tileKey`. A plot's `floors` counts the ones it added, and a resident's `floor` is the one they stand on. All are absent until used (the ground floor), so older logs hash as they did. `src/fixtures/floors-log.ts` pins a log that adds a floor, builds on it, puts up stairs, and walks up and about, and `floors.test.ts` its hash.
- A reader that means the ground floor keeps reading `state.blocks`. A reader that means any floor goes through `blocksOn`, `groundOn`, and `solidAt`; nothing else reaches into `state.floors`. A floor from an input becomes a key only after `floorOf` checks it: a whole number from 0 (`out_of_bounds`), at most `FLOORS.max` (`too_high`), one the plot added (`no_floor`). Absent is 0.
- `FLOORS` holds every number: one floor above the ground (`max`), 200 coins (`price`), walls holding flooring up within 2 tiles (`span`), and 4 wood for stairs (`stairsWood`), tuned with `scripts/economy-sim.ts` ([decision 0242](../../docs/knowledge/decisions/0242-a-storey-costs-200-coins-the-economy-run-with-builders-says-.md)) and pinned in `floors.test.ts`. `max` may go up, never down, since logged inputs on a floor must stay valid; once a live log holds an `add_floor`, `price` changes only behind a logged switch.
- `add_floor {px, py}` (`checkAddFloor`): from anywhere, on a plot you own or share, never the Commons (`plot_is_commons`), with coins open, below `FLOORS.max`, for `FLOORS.price`, split like a shop purchase (`treasuryShareOf` in `economy.ts` to the treasury, the rest burned, coin reason `floor`). It emits a public `floor_added` and makes the floor's empty layer. Nothing refunds a floor; `release` drops the plot's record and its count with it.
- `place`, `remove`, `lay`, and `lift` take `floor`, and their events carry it only above the ground floor. What holds a floor up: flooring upstairs needs a `wood`, `stone`, or `glass` block on the floor below within `FLOORS.span` tiles on the same plot, and a block upstairs needs flooring on its tile or such a wall right under it (`nothing_under`). Removing a wall or lifting flooring that is the last thing holding something up is `holds_up`. Planters, kitchens, workbenches, pedestals, frames, ponds, and candy bowls stay on the ground floor (`ground_floor_only`), since crops, crafting, displays, fishing, and candy are keyed by their tile alone. Hearths, crops, displays, and who stands where are checked on the ground floor only.
- `release` and `merge_resident` refuse while any floor of the plot holds anything (`plotHasAnything`).
- `stairs` (the end of `BLOCK_KINDS`) cost `FLOORS.stairsWood` wood, given back to whoever takes them up. They stand on the floor you climb from, need the floor above on the plot (`no_floor`; on the top floor, `too_high`), open air right above them, and upstairs flooring of their own. The tile above them is the stairwell: nothing is placed or laid there (`tile_occupied`). They're the one block anyone walks onto: `isSolid` and `solidAt` pass over them. Stairs or flooring someone online stands on can't be taken away (`holds_up`, at the foot of the stairs or at the top).
- `move up` from stairs goes to the stairwell above, and `move down` from a stairwell onto the stairs below (`checkClimb`); anything else is `no_stairs`, which names the way up from where you stand: this plot's stairs and the walk onto them, the `place` that would build a staircase, or the `add_floor` that comes before one (`upHint`, `downHint`, and `noFlooringHint` for a step upstairs with no flooring to land on, which `apply.ts` appends to the walk's refusal). Those words are a contract: `floors.test.ts` walks the whole way up by parsing them, so a reword that drops a call fails it. A step, a putter, and a routine's stroll keep to the floor you stand on, over `floorGround`: upstairs, a tile with no flooring (but the stairwell) is the obstacle `no_flooring`, so nobody walks off the flooring's edge or past a corner of it, and the planners never climb. `moved` carries `floor` only above the ground floor.
- Building reach counts a floor as a tile (`out_of_reach`). Who stands on a tile compares the floor; what's on a plot reads `x` and `y`. Jumps land on the ground floor and drop `floor`: `home`, `settle`, `visit`, `join_event`, `open_table` and `sit`, and a routine's `walk_home`. A resident who left upstairs comes back there while flooring is still under them, else at their hearth. Your hearth, and so the allowance and the pantry, is on the ground floor: standing over it upstairs is not home. Gathering and fishing need the ground floor, and so does knocking on a door (`ground_floor_only`).
- A `build` plan's tiles take `floor`, stairs included, and go in a fixed order: removals and lifts from the top floor down, then the ground floor's blocks and ground (the order plans always had, so older plans build and hash as they did), then each floor up's flooring and then its blocks. Each tile is checked against the plan's running view (`FloorView`, which the support checks take; `worldView` is the world as it is), so a plan can lift a loft's flooring and take away the walls under it in one call. A floor the plot hasn't added refuses the whole plan (`no_floor`), and so does one past the top (`too_high`), one that isn't a floor (`invalid_plan`), or a kind that can't go on its floor (`blockKindProblem`: `ground_floor_only`, stairs on the top floor or under a floor the plot lacks). What moves is skipped: a removal or lift that would leave flooring, a block, or someone on stairs (at the foot or the top) without what holds them is `holds_up`, flooring or a block nothing would hold up is `unsupported`, and a stairwell, or stairs with something above them, is `occupied`. Someone standing blocks a tile only on their own floor. Each list holds a whole plot on every floor (`planMax`), and `plotPlan` reads every floor back, `floor` on the entries above the ground floor. Town Hall builds stay on the ground floor.
- The API takes all of it: `add_floor`, `floor` on `place`, `remove`, `lay`, `lift`, and every plan entry, stairs, and `move` up and down, with the floor refusals, the `floor` coin reason, and the `unsupported` and `holds_up` skips in its lists. The protocol's `PLAN_MAX` is `planMax`, so a schema and a plan agree on a list's size. A floor from an input may be `undefined` in the command types (the protocol's optional fields), which `floorOf` reads as the ground floor.
- The client builds the same walking ground and climbs from its mirror with the sim's pure pieces: `groundOf` with `blocksWalkers` on the ground floor, `upstairsGroundOf` above it (what `floorGround` builds from the world), and `climbsAt`, which `checkClimb` reads too, for Go up and Go down, and `upstairsProblem`, to hold back Gather all and Fish upstairs.

## Resting (RFC 0044)

- `SEATS` in `src/furniture.ts` is every block `rest` puts you on and how (`sit`, or `lie` on a bed). The armchair, the sofa and the bed (`WALKED_ONTO_SEATS`) are walked onto like stairs, through `blocksWalkers`, so they never wall a room off and RFC 0032's notes read them as open. The chair and the bench stay solid: making them walked onto would change how logged walks replay. Only a kind added with the table joins `WALKED_ONTO_SEATS`.
- Resting is where you stand, never a field: someone on a seat's tile is resting on it, and any move takes them off, so nothing goes stale. `postureOn` says how; clients ask it of their mirror.
- `rest {x, y, floor?}` (`checkRest` in `src/rest.ts`): a seat on that tile and floor (`no_block`, `not_a_seat`), on the floor you stand on, one step away with that step open by `stepFrom` and the seat's tile counted open, so no corner is cut and no wall crossed (`out_of_reach`, naming the walk to a tile beside it that works), nobody online on it (`tile_occupied`), and not the one you're on (`already_there`). It emits `moved` and then a public `rested` with the seat's `block`. It pays nothing.
- The pieces take wood and `cushion`, a staple the shop sells for 5 coins and never buys back; their cards are on the shelf and on recipe page edition 3. `src/fixtures/cozy-log.ts` pins a log that places all three, rests on two, and walks out across the sofa, and `rest.test.ts` its hash.

## Roofs (RFC 0041)

- A roof belongs to a plot, not to its tiles: one `roof` field (`{style, material}`) set by `set_roof`, absent until one is set, so every older log hashes as it did and `REPLAY_VERSION` doesn't move (`roofs.test.ts` pins it with `src/fixtures/roof-log.ts`). `flat` is no roof and deletes the field.
- What a roof covers is read from the walls each time it's drawn, never stored (`roofShape`, `roofBoxes`, `roofSeat`): the box around each group of touching walls (diagonals count, `HOLDING_BLOCKS` from `floors.ts`) at least `ROOFS.minSpan` tiles across each way, on the highest floor whose walls hold one. So a home is roofed whole, doorway and all, a garden wall gets nothing, and taking a wall down never has to be checked against a roof. A home whose walls have all gone draws none and keeps the style its owner chose.
- A roof can wear one of `ROOF_TOPS` on its ridge (`PlotRoof.top`, `set_roof`'s optional `top`), free whatever the covering costs: a weather vane, a flag, or a bird's nest. It is part of the roof you set, so a `set_roof` without one leaves the ridge bare and every logged input from before it replays as it did, and `flat` takes it down with the roof. `roofShape` says where it stands (`top`, the first of the roof's highest tiles, so the north-west end of a gable's ridge rather than over the hearth), and every view draws it from there. A change to the ridge alone, on a roof keeping its style and covering, emits `roof_top_set` rather than `roof_set`, so a reader counting roofs doesn't count a new vane as a new roof. A change to the style or covering of a roof already up emits `roof_changed` instead (decision 0342), carrying the whole new roof; `roof_set` is a roof going up or coming down. No rule reads either.
- A roof wears the season the ground wears: `roofSnow(season)` is how far it goes toward `SNOW_WHITE`, all winter and none otherwise, and `roofTone(hex, season)` is that mix for a hex color. Every view reads it (the 3D views mix their own numeric colors with the same amount), so a winter town is snowed-over homes rather than summer colors on white ground. Presentation only, like the rest of `palette.ts`: no rule reads it.
- `roofShape` also gives each covered tile the height of its four corners, 0 at the eave and 1 along the ridge, from the style: `gable` one ridge down the box's longer way, `hip` four slopes, `pitched` one slope highest to the north. Every view draws from that one function, so the map, both 3D views, thumbnails, plot photos and pictures by link agree tile for tile.
- A roof's covering is any wall or window kind (`ROOF_MATERIALS`: the four free blocks and the made materials) and costs `blockNeeds(material)` times `ROOFS.blocks`, taken when it goes up and given back when it changes or comes down, the way a pond's stone is. So a free block roofs for free and works before items open, and a made material costs that material; changing style in the same material moves nothing.
- `set_roof {px, py, style, material}`: from anywhere, on a plot you own or share, never the Commons. A plot with nothing to roof is `nothing_under`, the roof it already has is `already_set` (as is `flat` on a home with none), a style or material the world doesn't know is `unknown_item`, and too little of the material is `not_enough_items`. `release` refuses while a plot has a roof (`plot_has_blocks`), since its covering would go with the record, so taking it down comes first, as clearing the blocks does. A plot with no upstairs may roof, and so may one whose top floor is a loft: the floor is never the gate ([decision 0324](../../docs/knowledge/decisions/0324-a-roof-is-a-look-on-the-plot-over-the-box-around-each-group-.md)).

## The market

- Nothing about the market runs until `open_market`, which needs the shop open and creates `state.market`. Until then old logs replay exactly; `src/fixtures/market-log.ts` pins a log with trades.
- A listed lot leaves the seller's things and lives in `market.listings` (escrow) until `unlist_item` gives it back (if there's room) or `buy_listing` moves it to the buyer. Listing needs a hearth and burns `MARKET.listingFee`. A sale pays the seller the price less `marketFee(price)`, which goes to the treasury in a line that names nobody.
- `listed`, `unlisted`, `listing_sold`, and `listing_removed` are public; `listing_sold` never names the buyer. Coin and inventory events stay private.
- `remove_listing` (staff, after a report) gives the lot back to its seller, or, when their things are full, marks the listing `takenDown` and keeps it out of `listingsOf` and `stallOf` until the seller collects it with `unlist_item`. Nothing goes past `inventoryMax`, and no coins move.
- Townsfolk never trade (`not_eligible`). The server adds two gates the sim can't see: time in Terrakin and karma for listing, and blocks for buying.

## Bounties and grants

- Nothing about bounties runs until `open_bounties`, which needs coins open and creates `state.bounties`. `grant` and `bounty` proposals are refused until then too. Until then old logs replay exactly; `src/fixtures/bounties-log.ts` pins a log with a bounty paid, one cancelled, and a grant.
- A bounty's reward leaves its poster's purse (or the treasury, for a town bounty) when it's posted and is held in the bounty until it's paid, cancelled, or expires. `bountyHeld` is part of the supply identity: `sum(coins) + treasury + bountyHeld == minted - burned`. `expectSupplyHolds` checks it.
- A resident's bounty is paid by its poster (`confirm_bounty`), a town bounty by a maintainer through the server (`confirm_town_bounty`, never the claimant, the proposer, or either's household). `to` must name the claimant in both, so a payout can't race a change of claimant. A maintainer sends a town bounty's claimant back with `reopen_bounty`.
- A passed `grant` doesn't pay at close: its coins go into a bounty with `grant: true`, held by its resident and marked done, and `confirm_town_bounty` releases it (coin reason `grant`, event `grant_paid`). It can't be claimed, dropped, or reopened, and doesn't expire.
- Grants and town bounties take only what the treasury holds above `ECONOMY.budgetReserve` (`treasurySpare`), when filed and when they close.
- Posting counts toward the poster's `giveCap`, paying toward the claimant's `receiveCap` (an owner pair skips it). Grants and town bounties come from the treasury and skip the caps. Townsfolk neither post nor claim.
- Open or claimed bounties expire at `new_day` once `expiresDay` comes; done ones wait. Only the `BOUNTIES.keepFinished` most recently finished bounties (by `closedDay`) stay in the world.
- `bountyMoves` and `postBountyProblem` run the commands' own checks without committing, so views offer only what the sim would accept.
- `bounty_posted` carries the bounty's words; the server strips them on the wire, like proposal titles.

## Hosted events

- Nothing about events runs until the first `schedule_event` or `schedule_town_event` creates `state.events` (`{nextId, list}`, ids `e_1`, ...). Until then old logs replay exactly; `src/fixtures/events-log.ts` pins a log that schedules, calls off, starts, samples, joins, ends, and voids events, the town's included.
- Hosting needs `townEligibility` (the Town Hall's rule) and a plot the host can build on, or the Commons. A start is on a whole minute, on a UTC day from `state.day` to 14 days on; the server checks the hour's notice, since the sim has no clock. At most 2 events per host on the calendar, one Commons event per host within 7 days, and 15 minutes between events at one place.
- The server logs an event's life: `event_start` (never before its day), `event_tick {event, slot}` at each 5-minute mark (each mark once, in order, none past the end), and `event_end`. A tick adds one to `seen` for each resident online in the area (the plot and 2 tiles around it), never the host or townsfolk. `attendNeeded` is 2 samples, or a third of them if that's more, counting at most 35.
- A Commons booking moves `EVENTS.deposit` out of the host's purse into the event (`event_deposit`). `eventHeld` is part of the supply identity. It comes back (`event_refund`) when `event_end` finds 3 attendees outside the host's household (`sameHousehold`), when the host calls it off before the event's day, or on `void_event`; otherwise it's burned.
- `join_event` puts a resident on the tile the server logged with it (`x`, `y`), which `joinTile` picks: on a plot someone lives on, where `visit` lands a visitor (`visitTile`), and in the Commons the free tile nearest the middle. The sim checks the logged tile (in the area, no block or building, no hearth, no other online resident) and never plans. An input without a tile, as in older logs, lands on the free tile nearest the plot's middle (`landingFor`), as it always did ([decision 0103](../../docs/knowledge/decisions/0103-join-event-lands-a-guest-where-visit-lands-a-visitor-logged-.md)). One already in the area is refused (`already_joined`) unless the input brings them back online, which `prepare` tells `check` (`rejoining`).
- `release` calls off the events on its plot, `unshare_plot` the unshared co-owner's there, and `new_day` drops events that finished more than 30 days before.
- `event_scheduled` carries where and when, never the words. `event_ticked` describes a sample; the server keeps it off the wire.

## Coins

- Nothing about coins runs until `open_economy`, which creates `state.economy`. Until then old logs replay exactly (`src/fixtures/pre-economy-log.ts` pins one with days, townsfolk, and a Town Hall). `src/fixtures/post-economy-log.ts` pins a log with coins moving, so a change to `ECONOMY` or a coin rule that would replay the live log differently fails a test. `ownerPairs` and `maintainers` are top-level keys, absent until set, and can be set before coins open. `ownerPairDays` records the day each pair first appeared; a pair skips the gift caps only from the day after. `add_owner_pair` and `remove_owner_pair` change one pair and leave the world exactly as `set_owner_pairs` with the whole new list would, so each link change logs one small input ([decision 0042](../../docs/knowledge/decisions/0042-owner-pairs-reach-the-sim-one-pair-at-a-time.md)). Keep them equivalent; a test compares the hashes step by step.
- `sum(economy.coins) + economy.treasury + bountyHeld + eventHeld == economy.minted - economy.burned` after every input. `economy.test.ts` checks it after each one.
- The allowance and the welcome gift are bookkeeping in `prepare()`'s commit, like `lastActiveDay`: the welcome gift is worked out before the command commits and is only paid in full (otherwise the resident waits in `economy.owed`, which `new_day` pays in order), and the allowance pays whenever a resident's own input (not `join` or `leave`) leaves them on their hearth. `home` while already home is accepted only when it collects the allowance.
- Purses are private. `state.economy` holds every purse and ledger, so the public world snapshot must drop it, keeping only the treasury (`treasuryOf`). A `coins` event belongs to its `residentId` alone: the server sends it only to that resident, never in the public broadcast, and never in another resident's action response or socket echo. A gift returns two `coins` events from one input, one for each side, so the giver's response must drop the receiver's (it carries their balance). `treasury` events and `economy_opened` are public. `owner_pairs_set`, `owner_pair_added`, `owner_pair_removed`, and `maintainers_set` stay on the server. Use `purseOf` for `GET /v1/purse`.
- The treasury's history is public: townsfolk budgets and their returns are one line each for all townsfolk together, and only welcome gifts name a resident. Their difference is the day's net of townsfolk tips and gifts to townsfolk, so the server keeps gifts with townsfolk on either side out of the public gift list and the public `gift` event, leaving that net unattributed.
- `daily_awards {day, awards}` mints coins the server counted for a day that has ended (appreciation, [decision 0055](../../docs/knowledge/decisions/0055-karma-is-scored-from-90-days-of-appreciation-outside-the-sim.md)). Each day is paid at most once and in order (`economy.awardedDay`, absent until the first). `ECONOMY.appreciationCap` may go up, never down, since replay checks every logged award against it.
- Townsfolk never save: at `new_day` a townsfolk resident's whole purse goes back to the treasury, including coins they held before joining the list, and leaving the list hands it back at once.
- Players see "coins", never "token".

## Pets

It meets every pet out today whose owner is online on the same green's ground floor (`met`, by id). A meeting counts between two households, neither townsfolk, and the first counted one of each pet's day sets its `metDay` and earns its owner `PROGRESS.petMeet` Hosting points (`petMeetEarns` in `levels.ts`), the walker's and the met owners' alike (`counted`). `pet_walked` is public, and both fields are absent until a walk, so older logs hash as before. `src/fixtures/pet-park-log.ts` pins a log of walks and meetings. `onGreen` is the same question for a reader with only the greens' middles, which the web uses.

## Fishing (RFC 0023)

- No switch: `fish` is a new command, `pond` a block `place` refused before, and the rod and the dishes recipes `craft` refused before, so old logs replay exactly. `src/fixtures/fishing-log.ts` pins a log with ponds dug, moved with a plan, and taken up, a rod made, a day of casts under different skies, fish sold, cooked, and given, the Town Hall digging in the Commons, and a winter char; `fishing.test.ts` checks its hash.
- A cast reads no clock, no weather, and no random number: the server logs `roll`, `weather`, and `timeOfDay` with it, and `checkFish` refuses (`server_only`) values it would never log. The season comes from `state.day`.
- Fish never run out. No pond holds a stock, so who casts first, or how often under the cap, changes no catch. Every cast counts whatever comes up: a fish comes with its caster's `inventory` event (reason `caught`), a boot is thrown back, and `fished` is public.
- Fish (`FISH_KINDS`, the role `fish`) stack and go on the end of `STACK_KINDS`. The town buys each season's own fish from the end of `SEASON_BUYS`, so every logged `sell_to_town` sees the kinds it saw.

## Pottery (RFC 0047)

- Nothing about pottery runs until `open_clay` (`checkOpenClay`, from `TOWN_ACTOR`, once items are open), which sets `items.clayOpen` (`clayOpen`). Before it, `place` and a `build` plan refuse a `kiln`, `craft` refuses a pot or a `glaze` on one, the pots' cards are on no shelf (`onShelf`'s `clay`), and `knows` says no to every pot, all with `pottery_closed` where it's a refusal, so a world without the switch reads and replays as it did and `REPLAY_VERSION` doesn't move. The server logs it only with its `clay` option, which no adapter sets ([decision 0362](../../docs/knowledge/decisions/0362-the-kiln-is-built-behind-open-clay-which-no-adapter-sets-unt.md)). `src/fixtures/kiln-log.ts` pins a log with clay gathered, a kiln placed, three pots fired across days under different rolls, and one given, listed, and shown; `pottery.test.ts` its hash and every refusal.
- How clay lies is `clayRule`: `open_clay` with `water`, which the server always sends, sets `items.clayByWater`, and clay then lies only on a tile beside water, a pond or the sea, any of the eight ways (`byWater`, over `fishing.ts`'s `isWater` and `waterBeside`), at `POTTERY.clayByWaterChance` (0.2) a day, and a resident picks up at most `POTTERY.clayPerDay` (6) a UTC day (`clay_limit`, counted in `items.today.clay`, absent until the first), which `gather` with no tile honours by leaving the rest lying, so moving a pond about can't farm it. An `open_clay` without `water` keeps the first rule, on any meadow or sand tile at `POTTERY.clayChance` with no cap, which only the kiln fixture's log has; it stays so that fixture's hash holds. Either way clay comes from a roll of its own and only on a tile whose find roll lands on nothing, whether finds are out or not, so turning it on moves no find, page, branch, or stone (`gatherableAt`'s `clay` and `water`, `pickupOn`'s). It's a resource like wood, so it earns no foraging points.
- A `kiln` (the end of `BLOCK_KINDS`) costs `POTTERY.kilnStone` stone through `blockNeeds` (2), or `POTTERY.kilnStoneFirstRule` (4) in a world whose clay came by the first rule (`blockNeeds`' `clay`, from `clayRule`), so the kiln fixture replays, given back to whoever takes it up, stays on the ground floor, and can't be taken up (or a plan's removal skips it, `growing`) while it holds a pot (`kilnRemoveProblem`).
- The pots are `POT_KINDS`, the goods whose recipe's station is `kiln`. `craft` at a kiln needs a plot the loader can build on and that isn't for sale (`not_your_plot`, `plot_listed`), since the pot comes back to them, checks a `glaze` from `GLAZES` and adds its one thing (`GLAZE_COSTS`, `withGlaze`) to the recipe's needs, refuses a second pot (`tile_occupied`), and makes the pot now (id, maker, label, glaze, the craft count, the points) into `items.firings` by tile (`loadKiln`), with a public `kiln_loaded` that says nothing of the pot. The bowl is everyone's once clay is out (`CLAY_BASE` in `recipes.ts`, frozen like the base), and the vase and teapot are cards.
- `harvest` on a kiln's tile goes to `checkOpenKiln`: `no_crop` when empty, `not_ready` before `readyDay`, `server_only` without a roll the server logged (and a roll on a planter's harvest is `server_only` too). The finish is `finishOf(roll)` through the frozen `FINISHES`; new odds are a new table behind a logged switch. The pot goes to whoever loaded it, held aside when someone else who can build there opens it and the loader is full, with a public `kiln_emptied` and an `inventory` (`fired`). `clear_block` refuses a kiln with a pot in it as `remove` does, `merge_resident` refuses a record with a pot firing, and `everyGood` counts a firing pot as its loader's.
- A pot is set down at home with `place {x, y, floor?, block: "pot", item, flower?}` (`POT_BLOCK`, the end of `BLOCK_KINDS`): after every check a block gets, `checkPlacePot` takes one of the actor's fired pots by id (a good of a `POT_KINDS` kind with a glaze) and, for a vase only, one of `FLOWER_KINDS` from their things, which goes on the good as `flower` and stays with it (`already_set` for a vase that has one). The good lives in `items.pots` by `potKey` (the tile key, `<floor>:<tile key>` upstairs), absent until the first, and `block_placed` carries it as `pot`. `remove` on the tile is `checkTakeUpPot`: back to whoever set it down, held aside when a co-owner takes it up and they're full. A `pot` block never comes from a plan or anything but `place` (`unknown_item`), a plan's removal skips one (`on_display`), `clear_block` refuses one (`potRemoveProblem`), `list_plot` refuses a plot with one down, `merge_resident` refuses a record with one down, and `everyGood` counts it as its placer's.
- A pot of tea (`TEA`, `pot_of_tea`, in the pottery family) is a kitchen recipe of 2 herbs that needs a `TEAPOT` in the brewer's things and leaves it there; nobody knows it before clay is out and everyone after (`CLAY_BASE`, `isPotteryRecipe`). `isDish` takes it. `bring_dish` from the host of a live event standing in its area, once clay is out, is `checkServeTea` in `thanksgiving.ts`: a pot of tea of theirs by id, once an event (`already_brought`), onto the event's `dishes`; anything else is `not_food`. `credit_event` then pays the host `POTTERY.teaPerGuest` (1) more Hosting a counted guest (`servedTea`, `eventCounts`' `tea`), and gives each guest it credits a `CUP` (`cup_of_tea`, a pottery keepsake with no recipe) made by the host (`pourTea`, an `inventory` event with reason `poured`, held aside for a guest whose things are full). Before clay, a host's `bring_dish` meets the feast's rules as it always did.
- Jobs' third edition (`POTTERY_JOB_EDITION`) is the second's table and `clem_bowl` and `ansel_vase`, bring jobs in the Making lane that `partOpen` puts up only once clay is out, so the edition without clay reads the second's boards, which `jobs.test.ts` pins to the same hashes.

## Party games

- Nothing about games runs until the first `open_table`, which creates `state.games`; no switch input is needed, since only new commands touch it. `src/fixtures/games-log.ts` pins a log with a whole Hearth race and a whole Lowest lantern, and `games.test.ts` its hash.
- A round is sealed: `table.sealed` holds each `decide` until `close_round`, and no event carries a choice before then (`decided` says only who). `round_closed` reveals them all at once, in seat order, with `null` for a seat that played the default. The order choices came in never matters.
- The server stamps `open_table`, `sit`, and `start_game` with its clock (`at`, in ms), `open_table` with its salt, and a `start_game` from anyone but the first seat with `free` once the start grace has passed; it decides when a round closes, and the sim never compares a time. `openedAt`, `roundAt`, and `readyAt` (when the table last came to have enough seats) are for the server's runner and views. The table keeps the salt as `secret`, in the hashed world so `/v1/health`'s hash can't be used to guess sealed choices; only `game_over` shows it. Its key must sort after `sealed`, since FNV-1a can be run backwards over known bytes: a secret before the choices would let the hashes before and after a `decide` give the move away. `games.test.ts` checks the order.
- Tables stand at `gameTableTiles` (in `world.ts`), which don't stop walkers. Once the server logs `keep_table_spots`, Town Hall builds keep them clear of blocks, so from then on moving a spot changes replay; `town.test.ts` pins them. A new table takes the first spot with no table and no block, and only a resident with a hearth opens one; `sit` puts a resident on the open tile nearest it. The first seat that isn't townsfolk starts the game (`starterOf`), townsfolk never do, and a table with nobody left but townsfolk closes in the same `stand`.
- Ratings ([decision 0096](../../docs/knowledge/decisions/0096-game-ratings-are-whole-number-elo-kept-in-the-sim-between-se.md)) are whole numbers, worked out at `game_over` from places, pair by pair within each ladder (`people:` or `agents:`, then the pace), scaled by the number of rated seats of that kind. Who's rated is fixed at `start_game`: residents who could vote in the Town Hall (`townEligibility`), not sharing a household with another seat (`oneHousehold`), under `GAMES.ratedPerDay`, in pairs under `GAMES.pairPerDay` and `GAMES.pairPerWeek`. `new_day` resets the day's counts; the week's (`games.week`, from a Monday by the UTC calendar) start again with the first counted game of a later week. Changing a number in `GAMES` or `GAME_RULES` changes how logged games replay, so it needs a logged switch.
- Finished tables move to `games.finished`, the newest `GAMES.keepFinished` kept, with their places, rating changes, and `endedAt` (the last `close_round`'s `at`).

## Levels (RFC 0029)

- Nothing about levels runs until `open_levels {firsts}`, which needs items open and creates `state.progress`. Until then no deed earns anything, `credit_event` is refused (`not_due`), and a title or an earned garment is `not_earned`, so old logs replay exactly. `src/fixtures/levels-log.ts` pins a log with the one-time credit, each kind of deed, a bounty week, a rated game, a credited event, a title, earned wear, a merge, and two seasons, and `levels.test.ts` its hash. The API carries all of it (`packages/protocol/src/levels.ts`, `packages/server/src/levels.ts`), and the server logs the switch only with its `levels` option, which neither adapter sets yet.
- Points are not coins. Nothing here mints, burns, or moves a coin or a thing, and `expectSupplyHolds` passes after every input in `levels.test.ts`.
- A level is never state. `levelOf(points)` reads it: level 1 with none, and going from level n to n + 1 takes `PROGRESS.step` (20) times n, with no top (level 2 at 20 points, 3 at 60, 5 at 200, 10 at 900). A resident's level reads all their points and a skill's level its own, on the same table (`levelsOf`). `levels.test.ts` pins the table; it may grow at the end and never change for a level anyone has reached.
- `state.progress.opened` is the world day `open_levels` was logged. `state.progress.points` holds each resident's points by skill (`SKILLS`: growing, making, foraging, hosting, playing; a skill at 0 is absent), and `firsts` the kinds they've had a first for, sorted. Points never go down.
- What earns, from `PROGRESS`, each added in the deed's own commit after every check of its own: a `harvest` 2 (Growing); a `craft` 2, however many it makes (Making); a find or a recipe page picked up with `gather` 4 and a fish caught 2 (Foraging); a lesson taught 8, a bounty paid 6, each counted guest at an event you hosted 2, and being a counted guest 8 (Hosting); a rated game finished 6, for a seat that chose in at least one of its rounds, and 2 more for finishing first, ties included, unless the game ended because every seat was away (Playing). A rated seat that sat down and never chose earns nothing, wherever the default left it. The numbers were tuned with `scripts/economy-sim.ts` ([decision 0246](../../docs/knowledge/decisions/0246-level-n-to-n-1-takes-20-points-times-n-a-lesson-and-a-counte.md)): rerun it before changing one. Wood, stone, an old boot, and everything else earn nothing: placing, planting, gifts, coins, sales, purchases, and learning a recipe.
- The daily cap: a skill counts at most `PROGRESS.dailyCap` (20) points a UTC day, kept in `progress.today` (absent until the day's first, dropped at `new_day`). A deed past the cap still happens and adds no points, and one that straddles it adds what room is left.
- Firsts: the first harvest of a crop, craft of a good, piece of furniture, or sweet, find, or fish of a kind earns `PROGRESS.first` (10) more, outside the cap, once per kind and resident. `firstSkill` says which skill a kind's first is; a recipe page has none.
- Who never earns: townsfolk, for any deed. A lesson counts only to a learner with a hearth outside the teacher's household (`sameHousehold`), and the learner earns nothing. A game counts only for seats `start_game` rated (decision 0096), which already leaves out households, townsfolk, and residents who couldn't vote. A routine's step is the server's, so it earns nothing.
- A resident's bounty counts for its claimant when the poster is outside their household, could vote in the Town Hall (`townEligibility`) when they pay, pays at least `PROGRESS.bountyMinReward` (5) coins, and no bounty from that poster counted for that claimant this UTC week. The week's pairs are in `progress.week` (absent until the first), written only when points were added, and they start again with the first counted bounty of a later week, as `games.week` does. A town bounty or a released grant counts every time.
- Hosting from events comes through `credit_event {event, guests}`, which the server logs after `event_end` with the guests it counted (ages, blocks, and two hosts a day are the server's to know). The sim takes the list only when the event has ended, on or after the day levels opened (`progress.opened`, `not_eligible` before), and wasn't credited before (`credited` on the event, absent until then), every guest is in the event's own `attended` (which never holds the host), none is in the host's household or townsfolk, and none is named twice. So the server can leave a guest out and never add one. The host earns for one event a UTC day and a guest once a UTC day (`progress.hostedToday` and `guestToday`, sorted, written only when points were added, dropped at `new_day`), both under Hosting's daily cap, which ends a host's points at ten guests. A town event has no host to earn. It emits `event_credited` with the list, then each `progress`.
- Titles: `TITLES` are fixed ids with fixed words (`TITLE_INFO`), one per skill at level 3 (`UNLOCKS.title`) and a second at level 10 (`UNLOCKS.master`). `profile` takes `title`: an id the resident's skill level has reached, or `null` for none. One short of the level is `not_earned`, an id that isn't a title is `invalid_profile`, and the title already shown is nothing to change. The title is kept in `progress.titles` (absent until the first; a resident showing none is absent), never on the resident, so `joined` and `profile_changed` never carry it; a change emits a public `title_changed`, and a `profile` that changes only the title emits no `profile_changed`.
- Earned wear: `join` and `profile` take a garment in `EARNED_WEAR` in a `wear` list once its skill (`EARNED_WEAR_SKILL`) is at level 5 (`UNLOCKS.wear`), and refuse it with `not_earned` before (`unearnedWear`, called beside the shop and partner wear checks). It takes a slot like any wear, is kept in the resident's `wear`, and takes a pattern and a color in `wearStyle`. It can't be bought, given, or listed, and it never comes off, since points never go down. Levels unlock nothing else: no action, coins, odds, or caps read a level.
- `merge_resident` adds `from`'s points to `into`'s skill by skill and joins their firsts, with a private `progress` for each skill and a `level_reached` where one went up, and moves `from`'s season points. It drops what only counts toward a day or a week (`today`, `hostedToday`, `guestToday`, the bounty week's entry as a claimant) and the title `from` showed. `retire_repeat_joins` treats a record with points or firsts as used: its id is in `state.progress`, which is "named elsewhere in the world".
- The one-time credit: `open_levels` carries `firsts`, a list of `{resident, kinds}` the server builds from the collection book (a server table, decision 0100, so it reaches the sim as data in the logged input). Each kind is worth a first's points in its skill and goes in that resident's firsts, so doing it again is no first. The sim refuses the whole input unless every resident is in the world, not townsfolk, and named once, with at least one kind, each a kind `firstSkill` knows and named once. The credit counts toward no day's cap and no season, and a second `open_levels` is `already_open`.
- Season points: `progress.seasons` keeps the points earned in each season since levels opened, keyed by the season's first world day (`seasonSpan(day).start`), then by resident and skill. Firsts count and the credit doesn't. It's absent until the first points after the switch. No rule reads it: it's history for a season board.
- Events: `progress` is private, like `coins` (its `residentId` alone), one per skill an input added to, with the points added, the `firsts` when there were any, the skill's `total`, and `today`'s count toward the cap. It's emitted only when points were added. `level_reached` is public: one for a skill and one for the resident (no `skill`), each naming the level they're at now, however many they passed. `levels_opened` and `title_changed` are public, and `event_credited` stays on the server.
- Once levels are open in a live world, changing a number in `PROGRESS` or `UNLOCKS`, the curve, a title's or a garment's skill, or what a first counts changes how logged inputs replay, so it needs a logged switch. A garment's slot may not change once someone wears it. `levels.test.ts` pins every number.

## Jobs (RFC 0030)

- Nothing about jobs runs until `open_jobs`, which needs levels open and creates `state.jobs` as `{opened, edition}`. Until then the board is empty, `take_job` is refused (`unknown_job`), `drop_job` and `hand_in` too (`no_job`), and no deed moves anything, so old logs replay exactly. `src/fixtures/jobs-log.ts` pins a log on top of the levels one with a job taken and let go, one held over midnight and finished by a find, a find taken on a day whose walk is one because the job for home is cranberries, three harvests, a night cast after a noon one, a made thing handed in, two lapses, a merge that moves a count, a rated game, a lesson, three fish with a boot between them, four weeks, and the title at ten jobs, and `jobs.test.ts` its hash. The API carries all of it (`packages/protocol/src/jobs.ts`, `packages/server/src/jobs.ts`, [decision 0260](../../docs/knowledge/decisions/0260-jobs-reach-the-api-behind-an-option-no-adapter-sets-with-fiv.md)), and the server logs the switch only with its `jobs` option, which the Worker sets, so terrakin.org has jobs, and the Node server leaves off ([decision 0262](../../docs/knowledge/decisions/0262-jobs-are-on-at-terrakin-org-the-worker-sets-jobs-the-node-se.md)).
- Jobs are not coins. Nothing here mints, burns, or moves one, and `expectSupplyHolds` passes after every input in `jobs.test.ts`. A thing handed in leaves the world.
- The board is never state. `jobsOn(state)` reads it from the world's day, the season and holiday that day and the days either side of it fall in, which parts of the game are open, and the edition's table: three jobs, the same for everyone, new at midnight UTC. Each of its three slots has two lanes that take turns by the day: home is Growing on even days and Making on odd ones, a walk is a fish and then a find, and neighbors is Hosting and then Playing. So every skill is up at least three days in seven, and no job comes up two days running. A lane gives its jobs that are up today in table order, one each turn. A season's jobs join their lane for the season. While a holiday runs, a lane with jobs for it gives one of those every other turn, so each comes up in the shortest holiday. In the first edition a lane's regular job is its turn's place in the day's list, which a holiday halves and a season's edge resizes, so the lane could go back to a job it just gave and leave one waiting 35 days. From the second edition each regular job is the next one up after the last one the lane gave (`carriedBoard`, counted from `state.jobs.opened` a stretch at a time between the days the jobs up can change), so none waits two rounds of its lane (`laneRound`): `jobs.test.ts` checks `jobWaits` from every day of four years and pins each job's longest wait [decision 0265](../../docs/knowledge/decisions/0265-the-jobs-board-s-second-edition-a-lane-s-regular-jobs-carry-.md). A job that needs a part the world hasn't opened is left out (finds for a find, lessons for a lesson, bounties for a bounty), and a lane with nothing up leaves its slot to the other lane every day.
- Every day's board has one job that needs nothing bought (`soloJob`): a find, a harvest of any crop or of one a starter seed grows, or a craft or a made thing of a recipe everyone knows that can be made from starter crops, the pantry's sugar and jars, wood, and stone. That's no seed from the shop, no recipe to learn, and no rod, so pumpkins, cranberries, candy, and the jack-o'-lantern aren't such jobs. The lanes' turns leave one kind of day without: an even day when Growing's turn falls on pumpkins or cranberries, beside a fish and a job for a host. On a day like that the walk is a find in place of the fish: in the first edition the first find up that day that the turns give neither the day before nor the day after, and from the second the finds lane's next find, when two or more are up, with the fish it stood in for coming on the lane's next turn. `jobs.test.ts` checks every day of four years, and that the swap is what makes it so. A world with no finds out has no find to give, and there the board is as the turns have it.
- The table is `JOB_EDITIONS`, by edition, and `state.jobs.edition` says which one the board reads. An edition is frozen once a live world reads it, since a logged `take_job` is checked against its day's board: `jobs.test.ts` pins the first edition's ids and a hash of all of it. A changed table is the next edition, switched on by the server-only `set_job_edition {edition}` from `TOWN_ACTOR` (`not_due` before jobs open, `server_only` for an edition that doesn't exist, `already_set` for the one in use; it emits a public `job_edition_set`), so days before the switch replay under the edition they had. A job's id and what it asks stay the same in every edition that has it (a test compares them), and `jobById` looks in all of them, so a job held across a switch still finishes. The second edition has the first one's jobs and reads them as above. Marlo's spring and summer find jobs joined the shared table before either season first came round in a live world, under RFC 0030's softer case, so no logged day's board changed ([decision 0268](../../docs/knowledge/decisions/0268-spring-and-summer-jobs-are-marlo-s-seasonal-finds-filled-in-.md)). `jobs.test.ts` pins a hash of each edition's boards for four years and puts a made-up edition after the newest for its own tests, and `src/fixtures/job-edition-log.ts` replays the switch and three jobs taken from the second edition's boards. The server logs the switch with its `jobEdition` option, right after a `new_day` [decision 0265](../../docs/knowledge/decisions/0265-the-jobs-board-s-second-edition-a-lane-s-regular-jobs-carry-.md). The first edition has no job for a counted guest or for a paid bounty ([decision 0255](../../docs/knowledge/decisions/0255-a-job-pays-10-points-and-three-count-a-week-the-economy-run-.md)): both deeds are in `JobDeed` and their hooks run, and `jobs.test.ts` proves them with the two jobs added in an edition of its own. Each job has a giver (one of `JOB_GIVERS`, a townsfolk's handle, fixed words that no rule reads), a skill, and either a `deed` to do `count` times or a `bring` recipe. No job holds resident text.
- `take_job {job}` holds one of today's jobs, from anywhere. It takes a hearth (`no_hearth`), and it's refused for townsfolk (`not_eligible`), while one is held (`job_held`), once the resident finished a job today or `JOBS.perWeek` this UTC week (`job_limit`, which says when the next can be taken), and for a job that isn't on today's board (`unknown_job`). `drop_job` lets it go and costs nothing. The held job is in `jobs.held` with the day and the input (`seq`) it was taken at and its `count` (absent until the first deed; the list is dropped when it empties), and it keeps its meaning after the board moves on.
- A deed job counts each deed that fits it from the moment it's taken, in the deed's own commit, after the deed's own points: a `harvest` (of any crop, or the job's `crops`), a `craft` of the job's recipe, a find or a recipe page picked up with `gather` (in the job's biome, or one of its `kinds`), and a fish caught (at the job's `timeOfDay`, which the server logs with each cast). Each hook reads the first half of the rule its deed's points read (`harvestCounts`, `craftCounts`, `pickupCounts`, `catchCounts` in `levels.ts`), so wood, stone, and a boot move nothing, and a deed past its skill's daily cap still moves the job. A deed moves only the job its own resident holds.
- The jobs with a second resident read their points' rule the same way, and that rule is what stops a household or a ring feeding itself. A lesson taught counts when the learner has a hearth and is outside the teacher's household (`lessonCounts`). A bounty counts for its claimant when the poster is outside their household, could vote, paid at least `PROGRESS.bountyMinReward`, and hasn't counted for them this week, and a town bounty or a released grant every time (`bountyCounts`, `townBountyCounts`). A rated game counts for a seat `start_game` rated that chose in at least one round, and Pip's win job only for first place (`gameCounts`, behind decision 0096's household rule and pair caps). An event counts through `credit_event`: `apply.ts` runs `creditJob` after the credit's own commit, for each guest on the server's list and for the host when the list holds at least the job's `guests` (`eventCounts`); the sim has already refused a list with a guest its samples didn't see, one in the host's household, or townsfolk. The credit comes in a later input than the event, so an event is dated by the input that ended it (`endedSeq` on the event, written at `event_end` only once jobs are open, so older events hash as they did) and a held job by the input that took it (`seq`): a job taken after the event ended doesn't move, and no job moves for an event that ended before `open_jobs`. Every other deed is reported in its own input. A game counts for a job held when it ends, whenever in the game the job was taken, and a bounty for a job held when it's paid, whenever the work was done. Points for one event a day as a host and one as a guest are a cap, like the daily one, so a second event that day still moves a job. Townsfolk never take a job and are never the other side: they know every recipe, so nobody teaches them, they're never rated, they never post a bounty, and they're never counted guests. A routine's step is the server's and no deed, so it moves nothing.
- `hand_in {item?}` finishes a bring job with a made thing of the job's recipe that its resident made: their oldest (made things' ids come from one counter), or the one `item` names. Without a bring job held it's `no_job`, for someone made townsfolk since they took it `not_eligible`, and with nothing of the kind that they made, or an `item` that isn't one, `nothing_to_hand_in`. The maker check is the anti-farming rule: a jar passed around a household finishes one job, its maker's. A bring job asks only for a made good, which carries its maker, never anything that stacks. `handInPick` makes every one of these checks and names the thing, so the server answers a `hand_in`, dry or real, with the thing the commit takes.
- Finishing a job, by a deed or a hand-in, takes it out of `jobs.held`, puts the resident in `jobs.doneToday` (sorted, dropped at `new_day`), adds one to their count in `jobs.week`, which starts again with the first job finished in a later UTC week, as `games.week` does, and one to their count for good in `jobs.total` (absent until the first; `jobsDone` reads it, and it's public). A job counts in the week it's finished in. It adds `JOBS.points` (10) to the job's skill through `jobEarns` in `levels.ts`: outside the daily cap, the way a first is, and counted in the season's points.
- At `new_day` a held job lapses once `JOBS.keepDays` (7) days have passed since it was taken, however many days the world skipped, with a `job_dropped` marked `lapsed` for each resident in id order. Nothing is lost with it.
- What the count unlocks, like a skill's titles and garment: fixed words, `not_earned` before the count, never sold, given, or listed, and never lost, since the count never goes down. `JOB_TITLES` are `helping_hand` at `JOBS.titleAt` (10) jobs and `pillar_of_the_town` at `JOBS.masterAt` (75), with their words, and which of those two numbers each one reads, in `JOB_TITLE_INFO`. `profile` takes one as `title` (`checkJobTitle`) and keeps it where a skill's title is kept, in `progress.titles`, so a resident shows one title at a time (`showTitle` in `levels.ts`, with the same public `title_changed`). `JOB_WEAR` in `looks.ts` is the `town_satchel`, an accessory, at `JOBS.wearAt` (25): `join` and `profile` take it in a `wear` list once the count is reached (`unearnedJobWear`, called beside `unearnedWear`). It's in `WEAR_ITEMS` and `WEAR_INFO` like any wear, so it takes a pattern and a color in `wearStyle`, once the count is reached: before it, `join` and `profile` refuse a `wearStyle` that names it at all (`not_earned`), a style and a `null` alike, so no logged input names the garment until someone has earned it. The free `satchel` is another thing and stays free. `JOB_TITLES` stays a list of its own beside `TITLES`, whose titles each have a skill and a level; `ShownTitle` is either, and `jobUnlocks` lists what the count unlocks in order.
- `merge_resident` adds `from`'s count to `into`'s, with a `job_total` for `into`, and drops the job `from` held, their place in `doneToday`, and their week's count (`mergeJobs`). The title `from` showed is dropped with the rest of `progress.titles`. A made thing keeps its maker's id through a merge, as all history that names `from` does, and `hand_in` counts a thing made by a record that was merged into the actor (`state.mergedResidents`) as the actor's own: a merge is one person's two records becoming one ([decision 0260](../../docs/knowledge/decisions/0260-jobs-reach-the-api-behind-an-option-no-adapter-sets-with-fiv.md)). A thing anyone else made is still refused. `retire_repeat_joins` treats a record named anywhere in `state.jobs` as used.
- Events: `job_taken`, `job_progress` (`count` of `of`), `job_done` (with the skill, the points, the week's count, and the count for good), and `job_dropped` belong to their `residentId` alone, like `coins` and `progress`. A `job_done` is followed by the private `progress` for its points and a public `level_reached` when a level went up. `jobs_opened` and `job_edition_set` are public. A handed-in thing leaves with an `inventory` event, reason `handed_in`.
- `JOBS` holds every number, pinned in `jobs.test.ts`: three on the board, one held, one finished a day, three a UTC week, seven days to keep, 10 points, and the counts for the two titles and the satchel. The first three say what shape the rules have and no rule reads them: three slots, one held job a resident, and a day's list that names a resident once. They were run through `scripts/economy-sim.ts` ([decision 0255](../../docs/knowledge/decisions/0255-a-job-pays-10-points-and-three-count-a-week-the-economy-run-.md)): rerun it before changing one. Once jobs are open in a live world, changing one of them, the lanes, a title's or the garment's count, or an edition a world has read changes how logged inputs replay, so it needs a logged switch. The garment's slot may not change once someone wears it.

## Circles (RFC 0033)

- Nothing about circles runs until `open_circles`, which needs days and coins and creates `state.circles` as `{opened, nextId, list}`. Until then every circle command and a `schedule_event` with `circle` is refused (`circles_closed`), so old logs replay exactly. `src/fixtures/circles-log.ts` pins a log that founds, invites, declines, cancels, forms, makes a steward, sets a hall, holds a circle night that counts, renames, takes a name down, lapses an invite, disbands one circle for not forming and another by staff, and `circles.test.ts` its hash. Its `CIRCLES_SETUP` is the world every test there starts from.
- A circle is in `list` by id (`c_1`, ...) with its `name` (resident text, absent after a takedown: `circleName` reads "Circle 1"), founder, status, `stewards` in the order they became stewards, `members` with the day and `seq` each joined (`membersByStanding` orders them), open `invites`, `hall` with the steward whose plot it is, `renamedDay`, and `gathered`, the Mondays of the counted weeks. A disbanded circle leaves the list. `leftDay` holds each resident's last leave or removal for the wait, and `nights` each resident's counted nights for the title. Membership is read from `list` (`circleOf`), never kept twice.
- Founding (`found_circle {name}`) needs `townEligibility`, no circle, no wait, and `CIRCLES.fee` coins, burned with a `circle_fee` coin line. While it forms, a member who isn't its founder chips in toward the fee with `chip_in_circle {circle, coins}`, paid to the founder (`circle_share`, kept in `chips`), up to the fee less `trialBurn` across members (`chip_in_full`). A circle disbanded unformed gives back all but `trialBurn`, minted (`refundFee`, `circle_refund`): each chip-in to its giver, the rest to the founder, to the record a merged one went into ([decision 0290](../../docs/knowledge/decisions/0290-a-kindred-that-doesn-t-form-gives-back-all-but-5-of-its-fee-.md)). The founder is the first steward, and any invites they held close (`circle_uninvited`, `joined`). A name is 3 to 32 characters after trimming, never "Circle N", and no other circle's with ASCII letters folded (`name_taken`); the server filters it first.
- Inviting needs a steward; the invitee needs a hearth, no circle, no wait, and isn't townsfolk; the circle needs room (`circle_full`, `household_full`, by `sameHousehold`) and fewer than `invitesMax` invites. An invite carries an optional `note`, the steward's words to the invitee, at most `noteMax` characters (`invalid_note`), kept on the invite and on its `circle_invited`; the server cleans and filters it first, as it does a gift's note. `join_circle` accepts an invite and checks the wait and the room again, closes the joiner's other invites, and forms the circle once its members come from `formHouseholds` households (`householdCount`), for good. Blocks are the server's to refuse.
- Leaving and removing (a steward removes a member who isn't a steward) set `leftDay`. A steward who leaves, is removed, or steps down takes their hall with them, and with no steward left the longest-standing member becomes one. The last member out disbands it (`empty`). A steward makes a member a steward up to `stewardsMax` and steps down only themselves, never as the only member. A rename comes once a UTC week (`weekStart`'s Monday to Sunday, `rename_limit`); the founding name is none.
- The hall is a plot a steward of a formed circle owns or shares, never the Commons, and one circle's at most. `release` clears every hall on its plot, `unshare_plot` the unshared steward's, and `merge_resident` the merged record's. A night stands only at the hall of a circle its host is in, so the circle's nights on the calendar are called off (`event_cancelled`) when its hall is cleared or moved and when it's disbanded, and a member's own nights when they leave or are removed (`nightsOff`).
- A circle night is `schedule_event` with `circle`: a member of a formed circle at its hall, no other one that circle has in that UTC week but a cancelled one (`night_this_week`). The hall stands in for a plot of the host's own; every other hosting rule stands. At a circle night the host is sampled like everyone (`presentAt`). `event_start` keeps who was in the circle then on the event as `kin`, and `event_end` replaces it with those of them, and of its members then, seen at `attendNeeded` samples, so leaving during a night never makes a member a counted guest at it. `event_started` and `event_ended` carry `kin` at a circle night. With `nightMembers` of them from `nightHouseholds` households the week goes into `gathered` once (the newest `gatheredKeep` kept) and each gets a night in `nights`, with a public `circle_gathered`. `credit_event` refuses a guest in `kin`. `circle_regular` comes at `regularAt` nights (`checkCircleTitle`), shown where every title is.
- At `new_day` a circle forming `formDays` after its founding is disbanded (`unformed`, its fee given back but `trialBurn`, `refundFee`), an invite lapses `inviteDays` after it was sent, and a wait that's over is dropped. `merge_resident` moves `from`'s nights, and its membership with its standing and stewardship unless `into` is in a circle or its household has no room, when it ends without a wait (`mergeCircles`).
- Events: every circle event names its circle. `circle_invited` and `circle_uninvited` are for the invitee and the stewards, and the server sends a forming circle's events only to its members and invitees. `circle_nights`, a merge's bookkeeping, stays on the server. `CIRCLES` holds every number, run through `scripts/economy-sim.ts` (decision 0279); once circles are open in a live world, changing one changes how logged inputs replay, so it needs a logged switch.

## Adding a kind

A new kind of thing is an entry in `src/catalog.ts`, on the end of `WRITTEN`:

1. One entry: a `fruit(...)` or `crop(...)` call for something that grows (it makes the seed too, and a fruit's jam comes from the jam family recipe), or an `entry(...)` with its name and plural, family, role, and, as it needs them, a recipe or a shop price with seasons or a holiday.
2. Its look: a template and colors (`produce`, `sprig`, `bloom`, `jar`), or `drawn` with a picture under its id in `packages/ui/src/item-art.ts`.
3. Decor, furniture and made materials are blocks too: their id goes on the end of `BLOCK_KINDS` in `types.ts`, with a color in `BLOCK_COLORS` and their 3D and plot photo pictures.

The tests that run over every entry cover the rest: ids, families, names, looks, seeds and crops that pair up, recipes from things that stack, a jam for every fruit, and a picture for every kind. Pomegranates and the jack-o'-lantern were added this way ([decision 0085](../../docs/knowledge/decisions/0085-furniture-keeps-its-own-role-in-decor-furniture-and-pomegran.md)), and so were Halloween's candy and decor ([decision 0107](../../docs/knowledge/decisions/0107-halloween-s-numbers-costumes-candy-decor-and-the-night-s-cap.md)), winter's cranberries, punch, decor, and candy canes ([decision 0124](../../docs/knowledge/decisions/0124-winter-s-numbers-cranberries-hot-cranberry-punch-winter-deco.md)), and the basket of fourteen crops with the ten recipes that use them ([decision 0308](../../docs/knowledge/decisions/0308-a-basket-of-fourteen-crops-sold-all-year-with-ten-recipes-an.md)). A new kind never joins a frozen list or what the town buys by being added: those are their own decisions. A new find lies nowhere until a new spawn table starts at a logged switch (`FIND_SPAWNS` is frozen), and `gather.test.ts` fails on a find that no table spawns. A new family recipe, template, role, or family is bigger and needs a decision record.

## Adding a command

1. Add it to `Command` in `types.ts`, plus any new `WorldEvent` and `RejectionCode`.
2. Implement the case in `check()` in `apply.ts`: validate everything and return a rejection, or return a closure that mutates and returns events. Do all reads in the check, not in the closure.
3. Test accept and every rejection path in `apply.test.ts`, plus a replay check if it touches new state.
4. Expose it in `packages/protocol/` (schema and `SKILL.md`, then `pnpm gen`) and render its events in `packages/client/src/mirror.ts`.

## Writing tests

A rule is tested here, at the lowest layer that catches its failure (the root [definition of done](../../AGENTS.md#definition-of-done)): a command through `apply`, with the world's hash checked after a refusal, and a pure function like `biomeAt` or `seasonOf` directly. Before you add a test, answer four questions, and leave it out while one has no answer:

1. What behavior does it protect: a rule, a refusal, a number, or a replay?
2. What change to the sim would make it fail?
3. Why doesn't a test already here catch that? A catalog fact belongs in `catalog.test.ts`, and a field a pinned hash covers needs no check of its own. Add a case to an existing test before writing a near-copy.
4. Does it need an export, flag, or hook that only tests use? Then test through `apply` instead.

Every fixture hash pin and replay test stays. A test in front of a guard (a cap, a limit, an owners-only rule) must fail when the guard is removed: remove it once and watch the test go red before you commit. A loop over thousands of cases collects what's wrong and checks the list once, instead of an `expect` each time.
