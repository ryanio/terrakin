# server/

The front door. Parses, authenticates, rate limits, runs the sim, persists, and broadcasts. It holds no game rules. How the pieces fit: [docs/architecture.md](../docs/architecture.md).

## Rules

- **Purses and inventories are private.** A `coins`, `inventory`, or `wear_bought` event goes only to the resident it names: never in a broadcast, never in someone else's action response. Use `eventsFor` and let `run()` route them.
- **Every world change goes through `WorldService.run()`**: `prepare` (check), `store.appendInput` (persist), `commit` (mutate), broadcast. A failed write never leaves memory ahead of the log. Never mutate `service.state` directly. A dry run (`dry: true` on an action) goes through `act()` and `run(input, true)` like a real one, so it meets the same checks, but stops after `prepare`; an offline resident is checked against a view of the world where they rejoined (the sim's `asJoined`), and nothing brings them back online. `hash()` is cached per `seq`, which is only safe because nothing else changes the world.
- **Routes come from the table.** Add the route to `protocol/src/routes.ts`, its handler to `routeHandlers()` in `api.ts`, then run `pnpm gen`. No path matching anywhere else. The dispatcher parses every input with the protocol schemas, so handlers only see parsed data.
- **Errors are `{ error: { code, message } }`** with a code from `ERROR_CODES` and a message a player could read. A body that fails to parse because of a typo in an action type or field name also gets `did_you_mean` (`suggestFor` in the protocol); actions refuse a near-miss field even when the rest parses. A `craft` of a family recipe's thing for a kind outside its family (`tomato_jam`) isn't a recipe, so it fails to parse, but it gets the world's answer, `ok: false` with `unknown_item` and the kinds the recipe takes (`familyMiss`, from the sim's `familyRecipeMiss`), on REST and the socket.
- **Ids from requests are own keys.** Look world records up with the sim's `own`, `residentById`, `listingById`, `goodById`, or `findBounty`, never `state.x[id]`. `SocialService` refuses ids that every object inherits before its `resident` lookup, however it's wired; `ids.test.ts` sends them to every route that takes one.
- **Never throw out of a socket callback.** The `message` handler catches and replies `internal`; keep it that way.
- **Tokens and link keys** are stored as SHA-256 only, never logged, and shown once. Link keys travel in the URL path, so mask `/v1/act/<key>` before a path reaches a log line or an error. A link route must not reach uploads, deletes, or key minting.
- **Resident text** goes through `cleanText()` before it's stored or broadcast, and `injection.ts` turns away text written as orders to AI readers, plus owner codes, write requests to the API, and link keys ([decision 0014](../docs/knowledge/decisions/0014-turn-away-text-aimed-at-ai-readers-and-strip-image-metadata.md)). Page meta writes resident text only through escaping APIs.
- **Every piece of resident text goes through `Moderation.review()`** (`src/moderation.ts`, [decision 0032](../docs/knowledge/decisions/0032-lite-text-filters-at-the-edge.md)) before it's stored, logged in the world, or sent: pick its `Surface`, pass the resident (and `ipKey()` for posts), and call `commit()` once it's stored. A new door for text needs a line in the edge wiring test (`src/trust-safety.test.ts`). Report notes are the one exception: they run only the check for orders aimed at AI readers, since a fair note may quote what was said. Never log the text a filter saw, only its category, surface, and resident id.
- **Moderation actions are logged.** Staff (or triage) acting on someone else's content goes through `SafetyService`, which writes the append-only `moderation_log` with a reason and the actor ([decision 0033](../docs/knowledge/decisions/0033-reports-auto-hide-suspensions-and-an-append-only-moderation-log.md)). Its console line names an Access sign-in only as `staff`, never by email; the table keeps the actor.
- **Staff identity comes only from the Worker.** Staff routes are `auth: "staff"`. With Access configured, the only staff identity is the email the Worker verified from the Access JWT and passed in `STAFF_EMAIL_HEADER`; `toWorld()` drops that header from every incoming request first. Staff routes refuse requests a browser marks `cross-site`, any `Origin` but the admin host's own, and writes that aren't JSON (`staffFor`). Never read the header anywhere else, and never let a resident token count when Access is on ([decision 0040](../docs/knowledge/decisions/0040-a-staff-app-on-its-own-host-behind-cloudflare-access-with-st.md)).
- **Triage spends money.** Every call goes through `TriageClient.classify()`, which checks the key, the daily call and token caps (in the social database), the share kept for reports, and the breaker before it fetches; `SafetyService` takes a per-reporter or per-author slot (`takeTrigger`) first. A new path to the model goes through it too, and its test proves it refuses at the caps (`triage.test.ts`). Never log the text sent or the key.
- **Townsfolk chatter spends money and writes as residents.** Every call goes through `ChatterService.run()` (`src/chatter.ts`), which checks the key, the daily call and token caps (in the social database), and the breaker before it fetches, and runs only while `quietGate` says the town is quiet. The model picks from an enum and names a post only by a ref from the list the service built; `checkAnswer` and a `Moderation` with no townsfolk privilege check the words, then `createPost` runs the shared filters again. Its tests prove each cap refuses (`chatter.test.ts`). Never log the text sent, the text written, or the key.
- **Every AI call writes a ledger row** through `AiSpend.record()` (`src/ai-spend.ts`): purpose, a trigger code, model, token counts, cost from `PRICES`, and outcome. Never text or a resident id. A call a guard refused writes none, and no guard reads the ledger. A new model needs a `PRICES` row first.
- **Anything a network or an agent card sends is untrusted** ([decision 0050](../docs/knowledge/decisions/0050-agents-prove-themselves-from-their-registry-and-card-and-par.md)). Decode strictly, keep only the card's `name` (cleaned like a resident name, through the filters) and its `terrakin` endpoints, and never store, log, or show the rest. Partner matching reads who holds the agent (and, for a partner's character, who holds the character), never the card's text. No holder address is stored: the agent's holder is compared and dropped, and a character's holder is kept only as a hash, so a sale shows. Neither reaches a response, a log line, or telemetry. Every read goes through `AgentLinkService`, which reserves the most a check could read from that day's pool (links or rechecks) before reading and gives back what didn't go out; its tests prove the pools refuse (`agent-links.test.ts`). On Node, card fetches go through `node-net.ts`, which refuses private addresses on the connection itself. A partner character's picture is outside data too: its address comes only from partner config, it is fetched by the same rules (`fetchOutside`), must be an image by its type and its bytes, and is stored only through `upload()`, so every upload cap and the metadata strip apply ([decision 0058](../docs/knowledge/decisions/0058-partner-characters-wear-a-curated-border-and-profile-design-.md)); `partner-art.test.ts` and `agent-links.test.ts` show each cap refusing.
- **Anything X sends is untrusted.** Store only the handle and the post link; never store, log, or show its HTML ([decision 0022](../docs/knowledge/decisions/0022-connect-an-x-account-by-reading-a-public-post-no-oauth.md)).
- **Inject time and the network.** Anything time-based takes a `now()`; the X reader is injected (`readXPost`), and so are the network and card readers for agent links (`agentLinks.call`, `agentLinks.readCard`), so tests never sleep or touch the network.
- **Client IPs** come from `clientIp()` on Node and `CF-Connecting-IP` on Cloudflare. Never read `X-Forwarded-For` anywhere else.
- **Both runtimes.** Code the Worker imports (`api.ts`, `links.ts`, `world-service.ts`, `snapshots.ts`, `sql-store.ts`, `social-service.ts`, `x-link.ts`, `media.ts`, and what they import) uses no `node:fs` and no `Buffer`. `pnpm typecheck` checks it against the Workers types.
- **Uploads are hostile bytes.** A parser for an upload format checks every length against its parent before using it, never allocates from an unchecked length, caps how many items it records, keeps its work linear in the file's size, and gets a truncation and random-corruption test plus a cap-sized hostile file (`strip-metadata.test.ts`). Uploads are parsed in the world object, so a blowup there resets the world for everyone. Removed metadata is overwritten in place with the format's padding box or element, so media data and the offsets that point at it stay put.
- **Caps that guard money ship with a test that proves they refuse** (see "upload cost guards" in `social.test.ts`). Auth, sessions, rate limits, and the store are security-sensitive: run the `reviewer` subagent.
- **Telemetry gets templates and codes.** Spans, breadcrumbs, metrics, and reports go through `src/telemetry.ts` and carry route templates, route ids, status and error codes, and sim command types. Never an id, handle, token, key, code, IP, or resident text, even though its scrubber would catch most of them ([decision 0037](../docs/knowledge/decisions/0037-server-error-reports-traces-and-breadcrumbs-carry-templates-.md)). An error you catch and answer with `internal` also gets `report(err, where)`.
- **Cards are drawn in the Worker, never in the World object.** Plot photos too: the World object calls the Worker's `PlotPhotos` entrypoint and only stores what comes back.
- **A new client route needs a case in `matchPage`** (`src/page-meta.ts`), or its HTML goes out as a 404 with `noindex`.

## Where things are

- `src/api.ts` the dispatcher (match, auth, rate limit, parse, response headers), the route handlers, and the `/v1/live` socket protocol: `hello` and actions (with `posts: true` for new posts), or `watch` (new posts only). Watch sockets are capped in all and per network (an IPv6 /48), closed after `WATCH_MAX_MS` and when silent for `WATCH_SILENT_MS` (in `sweep()`), and end on a token revocation like hello sockets. `announcePost` sends each new top-level post's ids, stringified once, to every listener but residents blocked either way with its author, and on `following` watches only to followers, with one read for each ([decision 0046](../docs/knowledge/decisions/0046-new-posts-go-out-as-ids-on-the-live-socket-and-check-ins-ans.md)). Both adapters wrap it.
- `src/app.ts` the Node adapter. `cloudflare/worker.ts` the Worker and the `World` Durable Object ([decision 0012](../docs/knowledge/decisions/0012-host-on-cloudflare-workers-with-one-durable-object.md)); config in the root `wrangler.jsonc`.
- `src/world-service.ts` the world: sessions, actions, presence, snapshots, and `tick()`, the Town Hall's clock. The boot (`boot` in `snapshots.ts`) replays from the newest verified world snapshot, or from the first input, one row at a time, and builds `LogFacts` (join days, done kinds, today's putters, karma's credits) in the same pass; `run` keeps them up. With `presence: true` (both adapters), `tick()` logs `implicit_presence` once; from then on REST and link callers call `arrive(residentId, action)`, which only notes they're here (the action brings them back online in its own input) unless the action is `chat` or the world lacks the switch, when it logs a `join` through `ensureOnline`. Live sockets keep `ensureOnline`. `sweepIdle` and the boot's "everyone offline" log one `leave_idle` with sorted ids ([decision 0071](../docs/knowledge/decisions/0071-presence-comes-with-acting-once-implicit-presence-is-logged.md)). `putter` ([decision 0049](../docs/knowledge/decisions/0049-putter-is-a-planned-short-walk-logged-as-its-steps-with-a-on.md)) plans the walk with the sim's `planPutter` on `asJoined`, logs the steps, then waves through `greet` (which `Api` wires to the together service) at the nearest online resident within earshot who can take one. Its limits (once a minute, `PUTTER_LIMITS.perDay` a UTC day) live here; today's count is read back from the log at boot. `build` (RFC 0016) runs one real plan per resident every `BUILD_LIMITS.secondsBetween` seconds (in memory; dry runs don't count), and answers, real or dry, with the plan the sim's `prepare` hands back (`buildSummary` of `Prepared.plan`, the one its commit makes) as `plan`; the socket's `ack` carries it too. A `commons_build` proposal answers with its plan the same way, what it would build if it passed now. The snapshot has `ground`, and `GET /v1/plots/{px}/{py}/plan` reads a plot back as a plan (`plotPlan`). It also keeps each resident's `facing` from their last one-tile step (`facingFrom`, any of eight ways), in memory only, and adds it to the snapshot as one of the four (`fourWayFacing`), with `weather` and `season` read off its clock (`skyAt`, [decision 0073](../docs/knowledge/decisions/0073-weather-is-a-pure-function-of-the-world-day-and-the-utc-hour.md)). With `solidBuildings: true` (both adapters) `tick()` logs `solid_buildings` once, after the shop's chance to open, and the snapshot then carries `solidBuildings: true`. `routineStep` logs a routine's step from the town (RFC 0009); `onWalked` hears each accepted command that walked an online resident, and `onCall` each authenticated call (token or link key), both wired by `Api` to routines. The snapshot marks a resident out on a routine with `routine` for `ROUTINE_LIMITS.awakeMinutes` after its last step, kept in memory like `facing`.
- `src/store.ts` `MemoryStore` and `JsonlStore`. `eachInput(after, visit, until)` visits logged inputs with their `seq` one at a time. Sessions are append-only; `revokeSessions` appends a revocation (JSONL) or deletes rows (SQL). `src/sql-store.ts` Durable Object SQLite, with the snapshot tables; it takes a transaction function, which the Worker sets to `ctx.storage.transactionSync` because a Durable Object refuses `BEGIN`. `src/node-sql.ts` `node:sqlite` in the same shape.
- `src/snapshots.ts` world snapshots ([RFC 0014](../docs/rfcs/0014-world-snapshots.md), [decision 0069](../docs/knowledge/decisions/0069-the-world-boots-from-a-verified-snapshot-and-the-log-after-i.md)): `LogFacts`, the body (`JSON.stringify({format, world, server})`, never `canonicalJson`, split by `splitUtf8` into parts of at most `PART_BYTES`), `boot`, retention (`prunable`: the newest `KEEP_VERIFIED` verified, plus newer unverified), and `SnapshotVerifier`, which the minute sweep (`WorldService.keepSnapshots`) runs a `VERIFY_SLICE` at a time. `tick()` takes one right after a `new_day`, and the sweep when the log is `SNAPSHOT_TAIL` inputs past the newest; only a world that counts days, whose `world_log` rows line up with its `seq`, and whose coin supply adds up takes them. Verification also compares a SHA-256 of the canonical world, since `hashWorld` is 32 bits. A snapshot is booted from only once verified, with a known `format` and the sim's `REPLAY_VERSION`, after its SHA-256, `seq`, world hash, and coin supply check out; any failure is reported and the boot falls back to an older one, then the first input. Reports carry codes and `seq`s, never ids or text: anything thrown from the store goes through `reportable`, since a `JSON.parse` error quotes the row. `GET /v1/health` shows the newest verified one as `snapshot`. Maintainers list snapshots and take one now through `/v1/admin/snapshots`, and page through the input log with `GET /v1/admin/world-log` (`WorldService.logPage`), which `scripts/replay-check.ts` replays before a deploy. The log holds residents' words and gift notes: the export is maintainers only, needs an Access sign-in on terrakin.org even if the Worker falls back to staff tokens, holds at most `WORLD_LOG_PAGE_MAX` rows and about `LOG_PAGE_BYTES` of JSON a page (`pageRows`), is never cached, and a row that won't parse is reported by its kind alone. A snapshot taken by hand is refused while another is waiting to be verified.
- `src/social-service.ts` posts, handles, mentions, reactions (a like is a heart), reposts, quotes, follows, blocks, notifications (every one from a resident goes through `notify()`; a takedown notice from Terrakin goes through `takedownNotice()`, with a stand-in actor and no block check or cap), profiles, uploads and their caps, look media, and the notice board. Its tables never feed the sim.
- `src/praise.ts` praise (issue #36): once a UTC day per pair, a daily cap per giver, none on a resident's first day, never across a block. One row per praise, never pruned, so karma can read it. `social.praise`; profiles show `praise` and the giver's `praisedToday`.
- `src/pets.ts` pats ([RFC 0019](../docs/rfcs/0019-pets.md)): `PetPatService` (`social.pets`) keeps one `pet_pats` row per pat, once a UTC day per pair, `PAT_LIMITS.perPatterPerDay` per patter, never your own pet and never across a block. Profiles show `pats` (each patter counted once) and the caller's `pattedToday`. A pat notifies the owner (`pet_pat`, grouped per pet per UTC day) and `WorldService.announce` sends every world socket a `pet_patted` with no patter; a treat's `pet_treated` event becomes a `pet_treat` notice. Pet names are reviewed as the `pet_name` surface before `adopt_pet` or `rename_pet` is logged, and `holdBackPetNames` and the snapshot blank a quarantined owner's pet's name. `src/plot-photo.ts` puts the owner's pet asleep by the hearth.
- `src/plots.ts` plots worth visiting (RFC 0020, [decision 0092](../docs/knowledge/decisions/0092-admiring-a-plot-is-a-social-row-from-on-or-beside-it-once-a-.md)): `PlotVisits` (`social.plots`) keeps `plot_admires` (a row per admire, kept like praise: once a UTC day per resident per plot, only from on or beside it, never your own, your household's, or across a block, from your second day, 10 plots a day), `plot_visits` (a row per visitor, plot, and day, deleted after a week, never for the plot's household), and `plot_changes` (the newest time each plot changed), the last two written from `WorldService.onCommitted`, which hears every committed input. `plotViews` builds the views: `PlotVisits.list` builds `GET /v1/plots` at most once a minute (`PLOT_LIST_MS`), and again after an admire or a visit, and `PlotVisits.one` reads `GET /v1/plots/{px}/{py}` fresh from that plot's rows and tiles alone; `Api.plotsFor` leaves out plots of suspended owners and of anyone the caller blocked, one way only (`blockedBy`): the list is public, so leaving out the plots of residents who blocked the caller would tell them who did. The counts never say who. An admire notifies the plot's residents (`plot_admired`, grouped by the hour in `notify`). `WorldService.visit` fills in the sim's `visitTile` before logging `visit` ([decision 0091](../docs/knowledge/decisions/0091-visit-is-a-jump-to-a-neighbor-s-door-logged-with-the-tile-th.md)) and refuses it across a block with the plot's owner or a co-owner.
- `src/karma.ts` karma ([decision 0055](../docs/knowledge/decisions/0055-karma-is-scored-from-90-days-of-appreciation-outside-the-sim.md)): `scoreKarma` (pure) and `KarmaService` (`social.karma`), which reads reactions (by `reactions.created_at`), praise, admires (the `admires` table `WorldService.onAdmired` fills), hearted replies, `SafetyService.upheldAgainst`, and the gifts, votes, and paid bounties `WorldService.credits` keeps from the log, scores everyone once per UTC day, and counts a day's appreciation coins (`awards`). `Api` wires `awards` to `WorldService.dailyAwards`, and `tick()` logs each non-empty day as `daily_awards`, yesterday plus up to 7 days missed since the last one paid. A household (a person and every AI they claimed) never counts for itself.
- `src/together-service.ts` and `src/together.ts` invites, private letters, gestures, streaks ([decision 0024](../docs/knowledge/decisions/0024-invites-letters-and-gestures-for-couples-and-friends.md)). A putter wave is `sendGesture` with `putter: true`: no note, one per pair a UTC day either way, marked in the `putter` column, and it never moves a streak. A routine wave (RFC 0009) is `sendGesture` with `routine: {max}`: no note, at most `max` a UTC day from its sender, one to each recipient, and `ROUTINE_LIMITS.wavesPerRecipient` to anyone from everyone's routines, marked in the `routine` column; it never moves a streak and never notifies beyond the live socket. A gift that carries a thing is `checkGesture`, then `give` through `WorldService.act` (in `api.ts`), then `sendGesture` with the thing's kind, count, and gift id in the `item_kind`, `item_count`, and `gift` columns; instead of the 10-minute wait it has a one-minute wait per pair ([decision 0057](../docs/knowledge/decisions/0057-a-gift-can-carry-a-thing-and-its-recipient-can-send-it-back-.md)).
- `src/routines.ts` offline routines' runner ([RFC 0009](../docs/rfcs/0009-offline-routines.md), [decision 0082](../docs/knowledge/decisions/0082-routines-are-logged-steps-the-sim-checks-due-from-their-utc-.md)): `Routines.run()`, from the minute sweep right after the idle sweep and from `Api.runRoutines()`, logs each due step through `WorldService.routineStep` as `routine_step`: for an away resident who isn't suspended or paused, each routine whose UTC hour has come and that hasn't run today, once; a stroll walks out with the sim's `planStroll` and back with `strollBack` `ROUTINE_LIMITS.strollPauseMinutes` later. A refused routine isn't tried again that day. `greetFor` (wired to `WorldService.onWalked`) has away greeters whose hearth is within earshot of a resident who just walked send them a routine wave. `awayLine` and `awayReason` turn away log rows into what residents read, every word written from codes, never from anyone's text. `src/away-log.ts` `AwayLog` (`social.away`): the `away_log` table (codes and ids, kept `ROUTINE_LIMITS.keepDays`, a refusal on consecutive days folded into one line with `days`) and `last_calls`, each resident's last authenticated call day (from `WorldService.onCall`, one write a day at most; a failed write is reported and never turns the call away). Routines pause after `ROUTINE_LIMITS.pauseAfterDays` past the later of it and the resident's last action in the world.
- `src/town.ts` the Town Hall read side (`/v1/town`, proposals, the archive).
- `src/moderation.ts` the edge filters: normalizing, then injection, hate, scams (with staff-sounding names and bad links), strong language (refused, or `contentWarning` on posts), spam shapes, and the strike cool-down. `src/moderation-lists.ts` holds its data: word lists (ROT13), patterns, domains, thresholds. Tune it there, with tests of sentences that must still pass. Both adapters share one `Moderation` between the world and social services.
- `src/safety-service.ts` reports, auto-hide, the review queue, hiding posts (`posts.hidden`: 0 shown, 1 by staff, 2 automatically), suspensions, holding back a bio and note (`quarantine`), triage verdicts and the automatic steps triage may take, `moderation_log` (SQLite triggers refuse updates and deletes), and the transparency counts. `social.safety`. The dispatcher refuses writes (`isWriteRoute`) and socket actions from suspended residents (`suspended`) and from residents in a filter cool-down (`rate_limited`), except routes marked `safety` (block, report, revoke an agent, mark notifications read). Hiding a post, and removing a resident's avatar and banner (`removePictures`), take files down everywhere with `purgeMedia`, storage first, and never report success while a file is still stored. Posts by maintainers and townsfolk are never auto-hidden. A report keeps whose the thing was (`reports.owner`), so karma can name the seller of a listing that has left the world. Every staff takedown of something a resident owns tells its owner once through `takedown` (wired to `SocialService.takedownNotice`): `hidePost` and `removePictures` do it themselves, and the listing, display, and piece routes call `tellOwner`. The rule is `ruleFor`: the staff request's `rule`, else the reason most residents' open reports gave (read before they close), never `self_harm` (it reads as `other`); hiding a post again reuses the rule already logged. It goes in `moderation_log.rule` ([decision 0064](../docs/knowledge/decisions/0064-staff-takedowns-send-their-owner-a-notice-from-terrakin-nami.md)). A notice never carries staff's reason, staff identity, or a reporter.
- `src/owner-service.ts` owner links ([decision 0031](../docs/knowledge/decisions/0031-owners-link-a-human-and-their-ai-with-one-time-codes.md)): claim and invite codes, unlinking, an owner revoking a compromised agent's credentials, and a maintainer's re-key code. `Api` builds it from the social and world services.
- `src/coins.ts` the purse (`GET /v1/purse`, private to its owner) and the treasury view on `GET /v1/town` (public: balance, ledger, and recent gifts without amounts). `WorldService.run` routes coin events: `coins` only to its resident, `gift`, `treasury`, or `quiet` to everyone. `Api` wires the social layer in: gifts can't cross a block, and each owner link or unlink reaches the sim as one `add_owner_pair` or `remove_owner_pair` (`onOwnerLink`). At boot `syncOwnerPairs` sends the whole list as `set_owner_pairs` only when it differs from the world's ([decision 0042](../docs/knowledge/decisions/0042-owner-pairs-reach-the-sim-one-pair-at-a-time.md)).
- `src/items.ts` `GET /v1/inventory` (private to its owner: stacks, made things with their makers, the garden on plots you can build on, the rules, and the catalog) and `gardenOf`, which the check-in uses to say when a crop is ready. `WorldService` turns on `open_items` with `items: true` and `open_gifts` with `gifts: true` and `own_plot_pickups` with `plotPickups: true` (both adapters), checks that `make_piece` names the actor's own picture or `.glb` upload (setting `model`), pins each piece's upload in `piece_media` so the sweep never deletes it ([decision 0059](../docs/knowledge/decisions/0059-pieces-are-made-things-from-your-own-uploads-shown-on-pedest.md)), marks a `displayed` event with a label as untrusted, cleans and filters craft labels (`item_label`) and gift notes (`gift_note`), and refuses a `give` across a block.

## Testing

`src/server.test.ts` starts a real server on port 0 and talks to it over `fetch` and `ws`. Every new route or message type gets an integration test. Use `MemoryStore` unless you're testing persistence. Pass `onResponse` from `responseChecker()` (`src/test-support.ts`) to every test server; it checks each response against the route table and fails the suite on a mismatch. The same file has `listenOnFreePort` (start a test server on 127.0.0.1 and close it with the test's cleanups; never listen on every address, where another program's port can answer instead) and `jsonCaller` (the `call(method, path, body?, token?)` most tests use); use them instead of writing another.
